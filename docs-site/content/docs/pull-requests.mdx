Totality Cloud writes a review summary into your pull request description and
answers questions when you mention `@gx` in PR comments.

A summary looks like this:

```markdown
> 🔴 👀 **Deep review** — clean rename in this repo, but indexed consumers still read the old field

Renames `amount_cents` → `amount` in the `payment.settled` event payload and
updates the emitter and its tests. Internally consistent — the risk is entirely
downstream.

## Blast Radius

🔴 HIGH (2 files, 1 area, +18/-11 lines).
3 consumers in `billing-dashboard` and `revenue-export` still read
`amount_cents` and default to 0 on a missing field.

## Notable Changes

- Renamed `amount_cents` → `amount` in the settled-event payload
  Attribution: codebase `internal/events/settled.go:34`
- Old field still read by 3 cross-repo consumers; none updated in this PR
  Attribution: codebase `billing-dashboard/src/ingest/settlement.ts:88`

*Generated by Totality.*
```

## Setup

1. `tl auth login` (or sign in on the console)
2. Install the Totality GitHub App on your account or organization:
   [github.com/apps/satoricorp-gx](https://github.com/apps/satoricorp-gx)
3. Publish through the hook: `git push` in a repo where `tl init` ran

A PR whose branch was never pushed through the pre-push hook gets no summary —
there is no captured context to summarize.

## PR summaries

The summary is written into the **pull request description**, not a comment.
Your own text stays above the Totality block; regeneration replaces only the
block. Do not seed a `## Summary` section — leave the body for your own notes.

What each section is:

| Section | Content |
| --- | --- |
| Verdict line | 🟢 **Quick scan** (LOW) / 🟡 **Careful pass** (MEDIUM) / 🔴 **Deep review** (HIGH), plus a one-line triage reason. The label always matches the Blast Radius level |
| Overview | one paragraph: what changed and why |
| Blast Radius | severity with file/area/line counts and a risk note. Judged by what the change can break — including code the diff never touches — not by diff size |
| Notable Changes | the changes a reviewer should look at first, each with an `Attribution:` line naming the concrete source: a codebase path, a captured agent session, a prior PR, or docs |

Summaries are generated when the GitHub App sees `pull_request`
`opened`/`synchronize` for a branch with published Totality context, and after a
publish when a PR already exists. Push again to force a refresh.

## Chat with @gx

Mention `@gx` in any PR comment:

```text
@gx which files should I review first?
@gx explain the auth callback changes
@gx what is the highest-risk change in this PR?
@gx are there missing tests?
```

Answers cite their sources: published revision diffs, changed hunks, PR comments,
the latest summary, and — when available — captured session context, indexed
codebase context, and previous findings. Because revisions carry session
provenance, `@gx` can answer what the author asked for and which commands and
tests ran.

### Retire a learned rule

```text
@gx skip rule never use var
@gx do not enforce this migration naming rule
```

When a matching active rule exists, it is retired and the override recorded.
Requires **write**, **maintain**, or **admin** permission on the repository.
