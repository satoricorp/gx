---
title: "GitHub PR summaries from Totality Cloud"
description: "How Totality Cloud writes a rich review summary into your pull request description after you publish with git push."
---

When a branch is published through Totality (`git push` with the pre-push hook) and a
GitHub pull request exists, Totality Cloud writes a single rich summary into the
**pull request description**, below anything you wrote yourself. The summary helps
reviewers see what changed, how risky it is, and where to focus — without you
authoring a description by hand.

## When this runs

Totality Cloud writes the summary automatically when:

- You `git push` a Totality branch (pre-push hook uploads the review artifact), and
- A pull request exists for that branch (`gh pr create` or the GitHub UI), or
- The GitHub App sees `pull_request` opened/synchronized for a branch that already has Totality context.

Your own PR description is preserved: the Totality-owned block sits below your text
behind a marker, and regenerating the summary replaces only that block.

## What the summary contains

- **Verdict line** — a severity dot and label that state what the change asks of a reviewer:
  - 🟢 **Quick scan** — LOW blast radius; safe to skim
  - 🟡 **Careful pass** — MEDIUM; needs a careful pass
  - 🔴 **Deep review** — HIGH; risky, prioritize review
- **Overview** — one paragraph on what changed and why
- **Blast Radius** — LOW / MEDIUM / HIGH with file/area/line counts and a risk note.
  Severity is judged by blast radius — what the change can break, including in code
  the diff never touches — not by how tidy the diff looks.
- **Notable Changes** — high-impact review targets, each with an **Attribution** line
  naming the concrete source that informed it: a codebase path, a captured agent
  session, a prior PR, or docs
- **Footer** — marks the block as generated by Totality

## Working with the summary

- Create or update the PR after publishing with `git push`.
- There is no `tl push`; plain `git push` is the publish path.
- Force a refresh by pushing again (or reopening the PR flow) so Cloud regenerates from the latest artifact.
- Write your own notes at the top of the PR description as usual — they survive every regeneration.
