# GX PR Body — Thesis Alignment Plan

This is a self-contained implementation plan that brings the `gx push` GitHub PR body in
line with the product owner's thesis. It builds directly on the machinery shipped by the
8-phase plan in `docs/internal/pr-summary-improvements-plan.md` (on the `bug/documentation`
branch); nothing here reinvents that machinery — it re-composes it into the layout the
owner asked for.

## Where the code lives (READ FIRST — every phase)

The implemented code is **not on `main`**. It lives on GX draft branches:

- `feature/codereview` — `internal/codereview` (triage, AI contract, sources, review policy)
- `feature/publication` — `internal/publication` (PR body, reach, golden corpus) and `REVIEW.md`
- `test/publication` — `internal/publication/github_pr_test.go`

**Setup for every phase** (stay on `main`; do not switch branches):

```sh
git checkout feature/codereview -- internal/codereview
git checkout feature/publication -- internal/publication REVIEW.md
git checkout test/publication -- internal/publication/github_pr_test.go
```

The publication code does not compile without the codereview restore (it references
`codereview.TriageChange`, `codereview.ReviewerFromEnvWithInfo`,
`codereview.ResolvedSourceLabel`, `codereview.AIReviewerWithOverview`,
`codereview.LoadReviewPolicy`, `codereview.LabelContextSnippets`). Restore all three
before touching anything. Do **not** touch unstaged user WIP files if present
(`.env.example`, `.github/workflows/macos-release.yaml`, `internal/telemetry/client.go`).

After each phase run:

```sh
go test ./internal/publication/... ./internal/codereview/... ./internal/cli/... ./internal/github/...
```

Version control uses GX: run `gx generate` after a phase's tests pass, then `gx push`.
Do not change the `<!-- gx:pr-summary:v1 -->` / `<!-- gx:author-notes -->` contract.

## The thesis (verbatim requirements)

> 0. We need an indicator of 'no review needed' -> 'Requires Deep Review' at the top to
>    indicate how important the PRs code changes are.
> 1. The summary should be short and brief. it should outline the purpose of the changes
>    in a short, digestable way.
> 2. We need a section for notable changes, with links to the specific LOCs in the PR. We
>    should not link entire files, that's not helpful.
> 3. We need a 'Blast Radius' section that identifies changes that are being made in the
>    PR and how much those effect the critical path. This should outline what changes are
>    going to effect the current status quo of the codebase, again, with attribution and
>    links to notable changes in the PR.
>
> The main things that we're missing are attribution and links. We need clearer sections
> that are easy to digest.

## Target PR body layout (the deliverable)

Concrete mockup of the ideal output. Every phase below exists to converge the renderer on
this shape. Sections top-to-bottom, no other top-level sections:

```markdown
<!-- gx:pr-summary:v1 -->

> 🔴 **Requires Deep Review** — security-sensitive change: session token validation altered in `internal/auth`.

Adds session-token validation to the login flow so expired tokens are rejected before
credential refresh. Motivated by the intermittent re-auth loop from the linked agent
session; centralizes expiry checks in `ValidateSession`.

## Notable Changes

- ⚠ [Session token validation now rejects expired tokens](https://github.com/acme/app/pull/20/files#diff-be70…R42) — verify login and refresh flows are not locked out.
  Attribution: session `sess-4f2a`; Google Engineering Practices
- [New `TokenClock` seam for expiry](https://github.com/acme/app/pull/20/files#diff-be70…R18) — injects time so expiry is testable.
- [Credential refresh no longer retries on 401](https://github.com/acme/app/pull/20/files#diff-9a1c…R77) — failures now surface to the caller.

## Blast Radius

Medium: 14 references to changed symbols across 6 other files; 3 file(s), +120/-38 lines.

- **Critical path `internal/auth/**`** — auth changes can leak, drop, or misuse credentials (REVIEW.md) — [changed here](…files#diff-be70…R42).
- **`ValidateSession`** — redefined in [session.go:42](…files#diff-be70…R42), referenced 9× across 4 files: [loginservice.go:88](…/blob/{headSHA}/internal/login/loginservice.go#L88), [middleware.go:31](…/blob/{headSHA}/internal/http/middleware.go#L31).

Reach is lexical (text search), not a dependency graph.

*Generated by GX — model gpt-4.1-mini; context: codebase, session.*
```

Layout rules:

- **Verdict banner** is the first visible line: blockquote + emoji + bold tier + one plain-English reason.
- **Purpose paragraph** is 2–4 sentences, purpose only. No blast radius, no "Context used:",
  no review-target counts. Those belong to Blast Radius and the footer.
- **Notable Changes** items always carry a validated `R{line}` hunk deep link. **Never a
  bare file link** (`#diff-{sha}` without a line anchor is a file link — banned here).
  Items that cannot be anchored to a line are dropped from this section.
- **Blast Radius** leads with the level+counts sentence, then critical-path lines (from
  `REVIEW.md` risk paths, each linked back to the PR hunk that triggered it), then symbol
  reach lines (definition hunk link + external blob permalinks), then the lexical
  disclosure line.
- **Provenance footer** unchanged (`provenanceFooter`, `pr_body.go:182`), absorbs the
  context-sources clause that today also appears mid-paragraph.
- `## Needs Review` disappears. Review-worthy AI findings render inside Notable Changes
  with a `⚠` prefix and their attribution line. The zero-target filler sentence
  ("No specific high-impact review targets…") is deleted; when nothing is notable the
  section is omitted entirely.

## Gap analysis (thesis item → today → gap)

### Item 0 — importance indicator at the top

**Today.** `reviewVerdict` (`pr_body.go:290`) renders `**Review verdict: {tier}** — {reason}.`
as the first line. Structurally this is the owner's indicator, and the logic (triage class,
risk level, strong/blocking findings, `aiSucceeded`) is sound.

**Gaps.**
- Tier wording doesn't match the owner's scale. The owner's top tier is **"Requires Deep
  Review"**; ours is `Full review`. `No review needed` matches.
- Reason strings leak internals: `docs-only-ai-failing/expected.md` reads
  *"changed files are documentation, text, license, image, or CODEOWNERS files; AI review
  unavailable"* and `high-reach/expected.md` reads *"default code review classification;
  quick scan recommended"* — triage `Rationale` strings (`triage.go:47-58`) were written
  as machine rationale, not reader-facing prose.
- Prominence: plain bold text; no visual weight distinguishing tiers.

### Item 1 — short, digestible purpose summary

**Today.** `openingSummary` (`pr_body.go:205`) prefers the AI overview, but **always
appends** `readinessSentence` (blast radius) and `contextSentence` into the same paragraph.
With AI unavailable the paragraph is pure template: *"This PR changes `docs`: clarify docs.
Blast radius is low (1 file(s), 1 area(s), +1/-0 lines), and GX did not isolate a specific
high-impact review target."* (every golden shows this shape).

**Gaps.**
- The paragraph mixes purpose with mechanics (blast radius, review-target counts, context
  sources). The owner wants purpose only.
- Blast radius prose is duplicated: once in the opening, once in the `## Blast Radius`
  section when reach exists.
- `contextSentence` duplicates the provenance footer's context clause.

### Item 2 — Notable Changes with LOC links, never file links

**Today.** No such section. Closest is `## Needs Review` — review *concerns*, not a digest
of what changed. Link behavior: AI findings with validated `{file, line}` get true
`R{line}` deep links (`hunkLinkForFinding`, `pr_body.go:1131`), and heuristic hunk items
use `prHunkSummary.Link` (line-anchored). But:

**Gaps.**
- There is no enumeration of *what changed*; a docs-only or clean PR renders only the
  filler line *"No specific high-impact review targets surfaced…"*.
- `hunkLinkForFinding` falls back to `githubFileDiffLink` (`pr_body.go:1161`) — a
  **file-level** anchor — when the finding's line doesn't validate. `renderPRResolvedSource`
  (`pr_body.go:1414`) has the same file-level fallback. Both violate the no-file-links rule
  for reader-facing sections.
- Attribution lines render plain paths (e.g. ``Attribution: codebase `internal/auth/session.go` ``
  in `risky-code-valid-anchor/expected.md`) instead of linking the line.

### Item 3 — Blast Radius with critical-path meaning, attribution, links

**Today.** `renderBlastRadiusSection` (`pr_reach.go:288`) renders only when
`reach.ReferenceCount > 0`, and only symbol + count + ≤2 blob permalinks
(see `high-reach/expected.md`). Reach feeds risk level via `applyLexicalReachToStats`
(`pr_reach.go:215`). `REVIEW.md` risk paths exist (`ReviewPolicy.RiskPaths`) and drive
Needs Review items via `hunkImpact` (`pr_body.go:508-515`) — but never appear in Blast
Radius.

**Gaps.**
- No *meaning*: the section never says which critical paths are affected or why a symbol's
  reach matters. Reference counts alone don't tell a reviewer what breaks.
- No attribution: symbol lines don't link back to the PR hunk that changed the symbol, and
  configured critical paths (the repo's own declaration of its critical path, via
  `REVIEW.md`) are absent.
- The section vanishes for most PRs (reach == 0), leaving blast radius information stranded
  inside the opening paragraph.

## Naming glossary

| Name | What it is |
|------|------------|
| Verdict tier | `No review needed` / `Quick scan` / `Requires Deep Review` (renamed from `Full review` in Phase 2) |
| Notable change | A rendered line in `## Notable Changes`: description + validated `R{line}` hunk link |
| `NotableChange` (JSON/Go) | New AI output element `{file, line, note}` (Phase 1); becomes a notable change only after anchor validation |
| Critical path | A `RiskPath{Glob, Message}` from `REVIEW.md` (`ReviewPolicy.RiskPaths`) — the repo's own definition of what must not break |
| Reach line | A Blast Radius line for one changed symbol: definition hunk link + external reference blob permalinks |

Do not introduce a second "highlights"/"key changes" noun; everything reader-facing is a
"notable change".

## Phase 4 — `## Notable Changes` (replaces `## Needs Review`)

**Goal:** the biggest new piece. A digest of what changed, every item deep-linked to a
specific LOC. All in `internal/publication/pr_body.go`.

### 4.1 Item type and selection

```go
type prNotableChange struct {
    Title        string          // one-line description (link text)
    Detail       string          // optional trailing clause after the em-dash
    Link         string          // REQUIRED validated R{line} link
    Flagged      bool            // true → render with ⚠ prefix (review-worthy)
    Score        int
    Attributions []prAttribution // reuse existing type (pr_body.go:109)
}

func notableChanges(artifact reviewbundle.Artifact, catalog prBodyCatalog,
    summary codereview.PRSummaryReview, summaryContext prSummaryContext,
    includeHeuristics bool, policy codereview.ReviewPolicy) []prNotableChange
```

Selection, in priority order (cap `maxPRNotableChanges = 7`, min target 3 when hunks exist):

1. **AI findings** (from `summary.Findings`) — today's `needsReviewItems` AI path
   (`pr_body.go:336-352`) carried over: same speculative/low-value/relevance filters, same
   `findingScore` + 1000 base, `Flagged: true`, attributions via `findingAttributions`
   (`pr_body.go:1362`).
2. **Heuristic risk items** — `heuristicNeedsReviewItems` (`pr_body.go:435`) carried over
   when `includeHeuristics` (same verdict gate as today), `Flagged: true` for warning-backed
   and risk-path items.
3. **AI notable changes** (from `summary.NotableChanges`, Phase 1) — `Flagged: false`,
   score 800, `Title` = sanitized `Note` (trimSentence 120), no Detail.
4. **Top-hunk fill** — when fewer than 3 items so far and hunks exist: largest hunks by
   `NewLines+OldLines`, `Title` = `"{revision description}: {path.Base(file)}"`
   (sanitized), score 400, `Flagged: false`, attribution
   `{Kind: "codebase", Label: "changed hunk", Ref: hunk.File}`.

Dedupe by validated link target (one item per `R{line}` anchor), then by lowercased title —
extend `dedupeNeedsReviewItems` (`pr_body.go:1658`) key to the link-first rule.

### 4.2 The no-file-links rule (hard requirement)

Every item's `Link` must be a **line-anchored** URL. Enforcement:

- Add `lineLinkForAnchor(prURL string, hunks []prHunkSummary, file string, line int) string`:
  returns `githubHunkLineLink` (`pr_body.go:1057`) **only** when
  `validatedHunkAnchor` (`pr_body.go:1117`) passes for `{file, line}`. When `line` doesn't
  validate but `file` matches a hunk, return that hunk's `Link` (already `R{ChangedLine}`,
  built by `githubHunkLink`, `pr_body.go:1028`) — a line link to the hunk's first changed
  line, honest and specific. When the file matches no hunk: return `""`.
- Rework `hunkLinkForFinding` (`pr_body.go:1131`) to use `lineLinkForAnchor`; **delete the
  `githubFileDiffLink` fallback at `pr_body.go:1161`**. Keep the lexical file-name search
  only for findings with empty `File`, but resolve the matched hunk through its
  line-anchored `Link`, never a file anchor.
- `notableChanges` drops any candidate whose resolved `Link == ""` (except when
  `pullRequestURL(artifact) == ""` — no PR URL means no links anywhere; render items as
  plain text rather than dropping them, matching the existing no-URL degradation in
  `renderPRResolvedSource`, `pr_body.go:1417`).
- Same rule inside attributions: in `renderPRResolvedSource` (`pr_body.go:1395`), replace
  the `githubFileDiffLink` fallback (`pr_body.go:1414`) with plain-text label (no link).
  Blob permalinks (`blobPermalink`, `pr_body.go:1067`) keep requiring `line > 0` for the
  `#L{n}` anchor; a blob link without a line anchor is allowed **only in attributions**,
  never as a Notable Changes item link.

- Finding with unknown file → dropped (not rendered unlinked, since hunks exist).
- `notable_changes` entry anchored → unflagged item; unanchored entry → dropped.
- Fewer than 3 anchored candidates → top-hunk fill items appear with revision-description
  titles.
- Empty-hunk artifact → section omitted.
- No PR URL → items render as plain text, zero links.

## Phase 5 — Blast Radius: critical paths, attribution, meaning

**Goal:** the section answers "what does this PR affect and why does it matter", with every
claim linked. In `internal/publication/pr_reach.go` (+ small `pr_body.go` plumbing).

### 5.1 Widen the gate

`renderBlastRadiusSection` (`pr_reach.go:288`) renders whenever triage class is `code` or
`security-sensitive` (thread the already-computed triage from
`renderGitHubPullRequestBody`, `pr_body.go:139` — do not recompute), **or** any
`policy.RiskPaths` glob matches a hunk, **or** `reach.ReferenceCount > 0`. Docs/config/
mechanical PRs with no reach and no critical-path hit keep omitting it.

### 5.2 Section contents (new signature)

```go
func renderBlastRadiusSection(artifact reviewbundle.Artifact, catalog prBodyCatalog,
    reach lexicalReach, policy codereview.ReviewPolicy, triage codereview.ChangeTriage) string
```

Top to bottom:

1. **Lead sentence** — the Phase 3 `readinessSentence` output (level + reach counts +
   file/line counts).
2. **Critical-path lines** (at most 4): for each `RiskPath` whose glob matches ≥1 hunk
   (reuse `codereview.MatchRiskPathGlob` exactly as `hunkImpact` does, `pr_body.go:508`):

   ```markdown
   - **Critical path `{glob}`** — {Message} (REVIEW.md) — [changed here]({first matching hunk .Link}).
   ```

   The hunk link is the attribution back to the PR (line-anchored per Phase 4 rule); the
   `(REVIEW.md)` suffix is the attribution of *why this is critical* (the repo's own
   policy). One line per risk path even when several hunks match; link the highest-scoring
   hunk (largest, or first).
3. **Reach lines** (at most 4, replacing today's symbol lines, `pr_reach.go:297-332`):

   ```markdown
   - **`{Symbol}`** — redefined in [{base(file)}:{line}]({definition hunk R-link}), referenced {N}× across {M} files: [{ref.File}:{ref.Line}](blobPermalink…#L{ref.Line}), […].
   ```

   Definition anchor: find the hunk whose file contains the symbol's `+func`/`+type` line
   (reuse `goPatchSymbolRE`, `pr_reach.go:25`, scanning `hunk.Patch`; compute the actual
   new-file line of the match by walking the hunk the way `changedLineForHunk`,
   `pr_body.go:1011`, does — extract that walk into a shared helper
   `lineOfPatchMatch(hunk, re) int`). When no defining hunk is found, render the symbol
   line without the "redefined in" clause (never guess). External references keep
   `blobPermalink` links with `#L{line}` (≤2 per symbol, as today).
4. **Disclosure line** — always when any reach lines rendered:
   `Reach is lexical (text search), not a dependency graph.` Keep the existing truncation
   sentence (`pr_reach.go:333-335`) appended when `Truncated`.

### 5.3 Session/context attribution

When the AI overview or a rendered finding carries a `ResolvedSource` with
`Kind == "session"`, `findingAttributions` already surfaces it on the Notable Changes item.
Blast Radius performs **no independent AI attribution** — its attributions are structural
(REVIEW.md, hunk links, blob permalinks). This keeps the section deterministic and
verifiable; do not add model-generated impact prose here.

### 5.4 Tests

- Risk-path repo fixture (reuse the `review-md-risk-path` golden's REVIEW.md): critical-path
  line renders with message, `(REVIEW.md)` attribution, and a line-anchored hunk link.
- Reach fixture (reuse `high-reach` setup): symbol line includes the "redefined in" hunk
  link and blob permalinks; symbol without a matched definition hunk renders without the
  clause.
- Code-change PR with zero reach and no risk-path hit → section renders with lead sentence
  only (level/counts) — the blast radius sentence must live somewhere.
- Docs-only PR → section absent.
- Disclosure line present whenever reach lines render.

## Phase order and dependencies

```
Phase 1 (shared contract: notable_changes, PRSummaryReview)
   │
   └──► Phase 4 (Notable Changes section — consumes PRSummaryReview)
Phase 2 (verdict tiers + banner) ── independent
Phase 3 (purpose-only opening; readiness sentence → blast radius lead)
   │
   └──► Phase 5 (Blast Radius meaning — extends the section Phase 3 feeds)
Phases 2, 4, 5 ──► Phase 6 (golden corpus — last, locks everything in)
```

Ship order: 1, 2, 3, 4, 5, 6. Each phase is one GX revision sized for one implementer
subagent (`gx generate` after its tests pass, then `gx push`). Phases 2 and 3 may note
"goldens updated in Phase 6" for golden-test failures they cause, but must keep all
non-golden tests green.
