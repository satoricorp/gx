---
title: "tl review"
description: "Review the current change with AI reviewers and repo context, use it as a CI gate, and rely on it leaving the repository untouched."
---

`tl review` reads the current change and reports what it found. It is the one
Totality command built to run anywhere — your machine, CI, or a checkout you do not
own — because it writes nothing.

```bash
tl review
```

By default it reviews the current change: uncommitted work if the tree is
dirty, otherwise the branch's commits against the base branch. Pass a prompt to
direct it:

```bash
tl review "check the auth rollback path"
```

## What it reads

The subject is resolved in this order:

1. `--base <ref>` when given — the range `<ref>...HEAD`
2. A dirty working tree
3. The branch's commits against an auto-detected base (`main`, `master`, `origin/main`, `origin/master`), or the last commit when HEAD already is the base branch

`--repo` overrides all of it and makes the repository itself the subject, which
is what questions about the codebase need when the working tree is dirty. Any
diff that was found stays in focus rather than being discarded.

If nothing was found at all, `tl review` says so. "Nothing was reviewed" is its
own outcome and never counts as a clean pass.

## Options

| Flag | Purpose |
|------|---------|
| `--scope <name>` | Focused lens: `architecture`, `security`, `performance`, `onboarding`, `docs`, `dependencies`, `testing`, `maintainability` |
| `--focus <path>` | Limit the review to files under a path prefix |
| `--base <ref>` | Review `<ref>...HEAD` instead of the working tree |
| `--repo` | Review the whole repository rather than just the current change |
| `--deep` | Full-spectrum review with more local and indexed context |
| `--verbose` | Include repo facts, docs, and changed files |
| `--json` | Print the report as JSON instead of markdown |
| `--fail-on <level>` | Exit non-zero when findings at or above this level survive |
| `--no-publish` | Skip posting the PR review comment and recording review history |

`tlr` is an alias for `tl review`.

## Using it as a CI gate

`--fail-on` turns a review into a gate. It accepts `any`, `speculative`,
`worth-exploring`, `strong`, `blocking`, and `none` (the default, which never
fails). The levels run most permissive first: `any` fails on anything the
review raised, `blocking` only on findings that should stop a merge.

```bash
tl review --base origin/main --fail-on strong --no-publish
```

Exit codes:

| Code | Meaning |
|------|---------|
| `0` | Reviewed, and nothing at or above the threshold survived |
| `3` | Findings at or above the threshold survived |
| `4` | Nothing was reviewed |

Exit `4` is deliberate and distinct. A gate that passes on a diff it never
opened is the silent false pass `--fail-on` exists to catch, so an explicit
gate fails rather than reporting success. Without `--fail-on`, both cases still
exit `0` so interactive use is unaffected.

A failing gate is the tool working, not an error. Totality uploads nothing when a
gate fails — no logs, no repo identity. Use `tl doctor --report` if you
actually want to send diagnostics to support.

## What it does not touch

`tl review` is read-only, and that is enforced by tests rather than intended by
convention:

- **No repository state.** It does not run `tl init`, install Git hooks, or
  create `.totality/` in the repo being reviewed.
- **No `.git/index`.** Plain `git status` and `git diff` rewrite the index stat
  cache and take `.git/index.lock`, which can collide with a concurrent Git
  command in CI. Review points its Git calls at a throwaway copy of the index,
  so your staged work and the real index are never touched.
- **No `$TOTALITY_HOME`.** It does not create `~/.totality`, mint a machine ID, or write
  telemetry state on a machine that has never run `tl`.
- **No uploads on failure.** Nothing is sent to Totality Cloud when a review fails.

Publishing is the one thing it does reach out for, and only on success: when a
matching pull request exists and you are authenticated, it posts the review
comment and records history. `--no-publish` turns that off, which is what you
want in CI.

## From an agent

The `tl_review` MCP tool runs the same command with `--no-publish` always set,
so an agent asking for review context never comments on a pull request.

```
tl_review(prompt: "check the auth rollback path", deep: true)
```
