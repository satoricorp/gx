<h2 id="target-audience">
  <a href="#target-audience">Target audience</a>
</h2>
<p>Conventional Comments is a standard for formatting comments of any kind of review/feedback process, such as:</p>
<ul>
<li><a href="https://en.wikipedia.org/wiki/Code_review">Code review</a></li>
<li><a href="https://en.wikipedia.org/wiki/Peer_review">Peer review</a></li>
<li><a href="https://en.wikipedia.org/wiki/Revision_(writing)">Revising</a> and <a href="https://en.wikipedia.org/wiki/Editing">editing</a></li>
<li><a href="https://en.wikipedia.org/wiki/Request_for_Comments">RFC</a></li>
</ul>
<h2 id="format">
  <a href="#format">Format</a>
</h2>
<p>Adhering to a consistent format improves reader&rsquo;s expectations and machine readability.
Here&rsquo;s the format we propose:</p>
<pre tabindex="0"><code>&lt;label&gt; [decorations]: &lt;subject&gt;

[discussion]
</code></pre><ul>
<li><em>label</em> - This is a single label that signifies what kind of comment is being left.</li>
<li><em>subject</em> - This is the main message of the comment.</li>
<li><em>decorations (optional)</em> - These are extra decorating labels for the comment. They are surrounded by parentheses and comma-separated.</li>
<li><em>discussion (optional)</em> - This contains supporting statements, context, reasoning, and anything else to help communicate the &ldquo;why&rdquo; and &ldquo;next steps&rdquo; for resolving the comment.</li>
</ul>
<p>For example:</p>


<div class="mx-4 my-4">
  <div class="p-2 border rounded flex cc-flatten-p dark:bg-gray-800">
    <img class="cc-avatar" src="/img/avatars/mouse.png" alt="A. Mouse" />
    <div class="w-full ml-2">
      <div class="text-gray-600 dark:text-gray-400">
        @amouse
      </div>
      <div class="cc-flatten-p">
        <p><strong>question (non-blocking):</strong> At this point, does it matter which thread has won?</p>
<p>Maybe to prevent a race condition we should keep looping until they&rsquo;ve all won?</p>

      </div>
    </div>
  </div>
</div>


<p>Can be automatically parsed into:</p>
<div class="highlight"><pre tabindex="0" class="chroma"><code class="language-json" data-lang="json"><span class="line"><span class="cl"><span class="p">{</span>
</span></span><span class="line"><span class="cl">  <span class="nt">&#34;label&#34;</span><span class="p">:</span> <span class="s2">&#34;question&#34;</span><span class="p">,</span>
</span></span><span class="line"><span class="cl">  <span class="nt">&#34;subject&#34;</span><span class="p">:</span> <span class="s2">&#34;At this point, does it matter which thread has won?&#34;</span><span class="p">,</span>
</span></span><span class="line"><span class="cl">  <span class="nt">&#34;decorations&#34;</span><span class="p">:</span> <span class="p">[</span><span class="s2">&#34;non-blocking&#34;</span><span class="p">],</span>
</span></span><span class="line"><span class="cl">  <span class="nt">&#34;discussion&#34;</span><span class="p">:</span> <span class="s2">&#34;Maybe to prevent a race condition we should keep looping until they&#39;ve all won?&#34;</span>
</span></span><span class="line"><span class="cl"><span class="p">}</span>
</span></span></code></pre></div><h2 id="labels">
  <a href="#labels">Labels</a>
</h2>
<p>We strongly suggest using the following labels:</p>
<table>
  <thead>
      <tr>
          <th></th>
          <th></th>
      </tr>
  </thead>
  <tbody>
      <tr>
          <td><strong>praise:</strong></td>
          <td>Praises highlight something positive. Try to leave at least one of these comments per review. <em>Do not</em> leave false praise (which can actually be damaging). <em>Do</em> look for something to sincerely praise.</td>
      </tr>
      <tr>
          <td><strong>nitpick:</strong></td>
          <td>Nitpicks are trivial preference-based requests. These should be non-blocking by nature.</td>
      </tr>
      <tr>
          <td><strong>suggestion:</strong></td>
          <td>Suggestions propose improvements to the current subject. It&rsquo;s important to be explicit and clear on <em>what</em> is being suggested and <em>why</em> it is an improvement. Consider using patches and the <em>blocking</em> or <em>non-blocking</em> <a href="/#decorations">decorations</a> to further communicate your intent.</td>
      </tr>
      <tr>
          <td><strong>issue:</strong></td>
          <td>Issues highlight specific problems with the subject under review. These problems can be user-facing or behind the scenes. It is strongly recommended to pair this comment with a <code>suggestion</code>. If you are not sure if a problem exists or not, consider leaving a <code>question</code>.</td>
      </tr>
      <tr>
          <td><strong>todo:</strong></td>
          <td>TODO&rsquo;s are small, trivial, but necessary changes. Distinguishing todo comments from issues: or suggestions: helps direct the reader&rsquo;s attention to comments requiring more involvement.</td>
      </tr>
      <tr>
          <td><strong>question:</strong></td>
          <td>Questions are appropriate if you have a potential concern but are not quite sure if it&rsquo;s relevant or not. Asking the author for clarification or investigation can lead to a quick resolution.</td>
      </tr>
      <tr>
          <td><strong>thought:</strong></td>
          <td>Thoughts represent an idea that popped up from reviewing. These comments are non-blocking by nature, but they are extremely valuable and can lead to more focused initiatives and mentoring opportunities.</td>
      </tr>
      <tr>
          <td><strong>chore:</strong></td>
          <td>Chores are simple tasks that must be done before the subject can be &ldquo;officially&rdquo; accepted. Usually, these comments reference some common process. Try to leave a link to the process description so that the reader knows how to resolve the chore.</td>
      </tr>
      <tr>
          <td><strong>note:</strong></td>
          <td>Notes are always non-blocking and simply highlight something the reader should take note of.</td>
      </tr>
  </tbody>
</table>
<p>If you like to be a bit more expressive with your labels, you may also consider:</p>
<table>
  <thead>
      <tr>
          <th></th>
          <th></th>
      </tr>
  </thead>
  <tbody>
      <tr>
          <td><strong>typo:</strong></td>
          <td>Typo comments are like <strong>todo:</strong>, where the main issue is a misspelling.</td>
      </tr>
      <tr>
          <td><strong>polish:</strong></td>
          <td>Polish comments are like a <strong>suggestion</strong>, where there is nothing necessarily wrong with the relevant content, there&rsquo;s just some ways to immediately improve the quality.</td>
      </tr>
      <tr>
          <td><strong>quibble:</strong></td>
          <td>Quibbles are very much like <strong>nitpick:</strong>, except it does not conjure up images of lice and animal hygiene practices.</td>
      </tr>
  </tbody>
</table>
<p>Feel free to diverge from this specific list of labels if it seems appropriate.</p>
<h2 id="decorations">
  <a href="#decorations">Decorations</a>
</h2>
<p>Decorations give additional context for a comment. They help further classify comments which have the same label (for example, a security suggestion as opposed to a test suggestion).</p>


<div class="mx-4 my-4">
  <div class="p-2 border rounded flex cc-flatten-p dark:bg-gray-800">
    <img class="cc-avatar" src="/img/avatars/ccat.png" alt="Cheshire Cat" />
    <div class="w-full ml-2">
      <div class="text-gray-600 dark:text-gray-400">
        @cheshirec
      </div>
      <div class="cc-flatten-p">
        <p><strong>suggestion (security):</strong> I&rsquo;m a bit concerned that we are implementing our own DOM purifying function here&hellip;</p>
<p>Could we consider using the framework instead?</p>

      </div>
    </div>
  </div>
</div>




<div class="mx-4 my-4">
  <div class="p-2 border rounded flex cc-flatten-p dark:bg-gray-800">
    <img class="cc-avatar" src="/img/avatars/ccat.png" alt="Cheshire Cat" />
    <div class="w-full ml-2">
      <div class="text-gray-600 dark:text-gray-400">
        @cheshirec
      </div>
      <div class="cc-flatten-p">
        <strong>suggestion (test,if-minor):</strong> It looks like we&rsquo;re missing some unit test coverage that the cat disappears completely.
      </div>
    </div>
  </div>
</div>


<p>Decorations may be specific to each organization. If needed, we recommend establishing a minimal set of decorations (leaving room for discretion) with no ambiguity.</p>
<p>Possible decorations include:</p>
<table>
  <thead>
      <tr>
          <th></th>
          <th></th>
      </tr>
  </thead>
  <tbody>
      <tr>
          <td><strong>(non-blocking)</strong></td>
          <td>A comment with this decoration <strong>should not</strong> prevent the subject under review from being accepted. This is helpful for organizations that consider comments blocking by default.</td>
      </tr>
      <tr>
          <td><strong>(blocking)</strong></td>
          <td>A comment with this decoration <strong>should</strong> prevent the subject under review from being accepted, until it is resolved. This is helpful for organizations that consider comments non-blocking by default.</td>
      </tr>
      <tr>
          <td><strong>(if-minor)</strong></td>
          <td>This decoration gives some freedom to the author that they should resolve the comment only if the changes end up being minor or trivial.</td>
      </tr>
  </tbody>
</table>
<p>Adding a decoration to a comment should improve understandability and maintain readability. Having a list of many decorations in one comment would conflict with this goal.</p>
