effective, understandable, maintainable, and secure.</p><h2 id=getting-your-merge-request-reviewed-approved-and-merged>Getting your merge request reviewed, approved, and merged</h2><p>Before you begin, familiarize yourself with the
<a href=/development/contributing/merge_request_workflow/#contribution-acceptance-criteria>contribution acceptance criteria</a>.</p><p>Have your code <strong>reviewed</strong> by a
<a href=https://handbook.gitlab.com/handbook/engineering/workflow/code-review/#reviewer>reviewer</a>
from your group or a <a href=/development/code_review/#domain-experts>domain expert</a>.</p><p>For small, straightforward changes, you can skip the reviewer step and go directly to a
<a href=https://handbook.gitlab.com/handbook/engineering/workflow/code-review/#maintainer>maintainer</a>.
Examples of small and straightforward changes:</p><ul><li>Fixing a typo or making small copy changes.</li><li>A tiny refactor that doesn&rsquo;t change any behavior.</li><li>Removing a feature flag that has been default-enabled for more than one month.</li><li>Removing unused methods or classes.</li><li>A well-understood logic change that requires changes to fewer than five lines of code.</li></ul><p>Otherwise, have a reviewer in each <a href=/development/code_review/#approval-guidelines>category</a> the MR touches before passing
to a maintainer. For security assistance, include <code>@gitlab-com/gl-security/appsec</code>.</p><p>After the reviewer approves, a maintainer reviews and merges. The last required approver merges.</p><p>For CODEOWNERS-required approvals, seek domain-specific approvals before generic ones.
Domain-specific approvers who are also maintainers should review both aspects and approve once.</p><h3 id=approval-guidelines>Approval guidelines</h3><p>As described in the section on the responsibility of the maintainer below, you
are recommended to get your merge request approved and merged by maintainers
with <a href=/development/code_review/#domain-experts>domain expertise</a>. The optional approval of the first
reviewer is not covered here. However, your merge request should be reviewed
by a reviewer before passing it to a maintainer as described in the
<a href=/development/code_review/#getting-your-merge-request-reviewed-approved-and-merged>overview</a> section.</p><div class=table-container><table class=docs-table><thead><tr><th>If your merge request includes</th><th>It must be approved by a</th></tr></thead><tbody><tr><td><code>~backend</code> changes <sup>1</sup></td><td><a href=https://handbook.gitlab.com/handbook/engineering/projects/#gitlab_maintainers_backend>Backend maintainer</a>.</td></tr><tr><td><code>~database</code> migrations or changes to expensive queries <sup>2</sup></td><td><a href=https://handbook.gitlab.com/handbook/engineering/projects/#gitlab_maintainers_database>Database maintainer</a>. backend review.</p><p>For Haml template changes specifically:</p><ul><li><strong>Request backend review</strong> when changes include Ruby logic, method calls,
variable assignments, conditionals, loops, data preparation, security checks,
or any server-side processing in the template.</li><li><strong>Request frontend review</strong> when changes affect DOM structure, CSS classes,
HTML attributes, accessibility features, user interactions, and responsive design,
or visual presentation.</li><li><strong>Request both reviews</strong> for complex changes that involve both Ruby logic and significant UI modifications, or when
backend and frontend are intertwined (such as when backend serves data that is consumed by Vue or JavaScript), to
ensure both the backend functionality and frontend user experience are properly evaluated.<ul><li><strong>Example:</strong> A Haml template that calls Ruby methods to prepare data attributes for
a Vue.js component (for example, <code>project_id: @project&.to_global_id</code>) would benefit from a backend review for Ruby logic
correctness and frontend review for the component integration.</li></ul></li></ul></li><li><p>We encourage you to seek guidance from a database maintainer if your merge
request is potentially introducing expensive queries. It is most efficient to comment
on the line of code in question with the SQL queries so they can give their advice.</p></li><li><p>User-facing changes include both visual changes (regardless of how minor),
and changes to the rendered DOM which impact how a screen reader may announce
the content. Groups that do not have dedicated Product
Designers do not require a Product Designer to approve feature changes, unless the changes are community contributions.</p></li><li><p>End-to-end changes include all files in the <code>qa</code> directory.</p></li></ol><h3 id=reviewing-a-merge-request>Reviewing a merge request</h3><p>Understand why the change is necessary (fixes a bug, improves the user
experience, refactors the existing code). Then:</p><ul><li>Be thorough to reduce the number of iterations.</li><li>Communicate which ideas you feel strongly about and those you don&rsquo;t.</li><li>Identify ways to simplify the code while still solving the problem.</li><li>Offer alternative implementations, but assume the author already considered
them. (&ldquo;What do you think about using a custom validator here?&rdquo;)</li><li>Seek to understand the author&rsquo;s perspective.</li><li>Check out the branch and test the changes locally. For MRs requiring significant
GDK modifications, consider requesting screenshots, videos, or domain-expert verification
instead. Your testing might result in opportunities to add automated tests.</li><li>If you don&rsquo;t understand a piece of code, <em>say so</em>.</li><li>Use the <a href=https://conventionalcomments.org#format>Conventional Comment format</a> to convey intent.
Mark non-mandatory suggestions as (<code>**non-blocking:**</code>). When only non-blocking suggestions remain,
move the MR to the next stage rather than waiting.</li><li>Ensure there are no open dependencies. Check <a href=/user/project/issues/related_issues/>linked issues</a>
for blockers. If blocked by open MRs, set an <a href=/user/project/merge_requests/dependencies/>MR dependency</a>.</li><li>After a round of line notes, post a summary note such as &ldquo;Looks good to me&rdquo; or &ldquo;Just a couple things to address.&rdquo;</li><li>Let the author know if changes are required following your review.</li></ul><div class="alert alert-type-warning gl-rounded-lg"><div class=alert-icon></div><div class=gl-min-w-0><p><strong>If the merge request is from a fork, also check the <a href=/development/code_review/#community-contributions>additional guidelines for community contributions</a>.</strong></p></div></div><h3 id=gitlab-specific-concerns>GitLab-specific concerns</h3><p>GitLab is used in a lot of places, from <a href=https://about.gitlab.com/install/>Omnibus packages</a>,
to <a href=/install/self_compiled/>source installations</a>.
GitLab.com itself is a large Enterprise Edition instance.
This has some implications:</p><ol><li><strong>Query changes</strong> should be tested to ensure that they don&rsquo;t result in worse
performance at the scale of GitLab.com.
See <a href=/development/database_review/>database review guidelines</a>.</li><li><strong>Database migrations</strong> must be:<ol><li>Reversible.</li><li>Performant at the scale of GitLab.com - ask a maintainer to test the
migration on the staging environment if you aren&rsquo;t sure.</li><li>The correct migration type. See the guidance to choose which
<a href=/development/migration_style_guide/#choose-an-appropriate-migration-type>migration type</a>.</li></ol></li><li><strong>Sidekiq workers</strong> <a href=/development/sidekiq/compatibility_across_updates/>cannot change in a backwards-incompatible way</a>.</li><li><strong>Cached values</strong> may persist across releases. If you are changing the type a
cached value returns (say, from a string or nil to an array), change the
cache key at the same time.</li><li><strong>Settings</strong> should be added as a
<a href=https://handbook.gitlab.com/handbook/product/product-principles/#convention-over-configuration>last resort</a>. See <a href=/development/architecture/#adding-a-new-setting-in-gitlab-rails>Adding a new setting to GitLab Rails</a>.</li><li><strong>File system access</strong> is not possible in a <a href=/development/architecture/#adapting-existing-and-introducing-new-components>cloud-native architecture</a>.
Ensure that we support object storage for any file storage we need to perform. For more
information, see the <a href=/development/uploads/>uploads documentation</a>.</li></ol><h3 id=the-responsibility-of-the-merge-request-author>The responsibility of the merge request author</h3><p>You are the <a href=https://handbook.gitlab.com/handbook/people-group/directly-responsible-individuals/>directly responsible individual</a>
(DRI) for finding the best solution. Stay as the assignee throughout the review lifecycle.
If you cannot set yourself as an assignee, ask a
<a href=https://handbook.gitlab.com/handbook/engineering/workflow/code-review/#reviewer>reviewer</a> to do it.</p><p>Do not submit a merge request that is too large, fixes multiple issues, has high
complexity, or implements more than one feature.</p><p>If the MR touches multiple CODEOWNERS sections, to minimize the approvals needed consider
splitting the MR by concerns to parallelize reviews.
Before requesting a maintainer review, confirm:</p><ul><li>The MR solves the intended problem in the most appropriate way.</li><li>All requirements are satisfied.</li><li>No remaining bugs, logic problems, uncovered edge cases, or known vulnerabilities exist.</li></ul><p>Self-review your MR following the <a href=/development/code_review/#reviewing-a-merge-request>Code Review</a> guidelines.
Add inline comments on lines where you made decisions or trade-offs,
or where context helps the reviewer understand the code.</p><p>Involve <a href=/development/code_review/#domain-experts>domain experts</a>, product managers, UX designers, and database specialists
as appropriate. If you are unsure whether your MR needs a domain expert review, it does.</p><p>For features spanning 10 or more MRs, work with your EM or Staff Engineer to identify
consistent maintainer who share the context.</p><p>If your MR touches multiple domains, request a review from an expert in each domain.</p><p>Before requesting review, add MR diff comments for:</p><ul><li>Added linting rules (RuboCop, JS, and so on).</li><li>Added libraries (Ruby gems, JS libs, and so on).</li><li>Links to parent classes or methods, where not obvious.</li><li>Benchmarking results.</li><li>Potentially insecure code.</li></ul><p>Ensure reviewers have access to any projects, snippets, or assets needed to validate the solution.</p><p>When assigning reviewers, comment to specify which domain each reviewer should focus on.
This avoids ambiguity when a team member has expertise in multiple areas.
For examples, see <a href=https://gitlab.com/gitlab-org/gitlab/-/merge_requests/75921#note_758161716>MR 75921</a>
and <a href=https://gitlab.com/gitlab-org/gitlab/-/merge_requests/109500#note_1253955051>MR 109500</a>.</p><p>Only add <code>TODO</code> comments to source code if a reviewer requires it.
If you add a <code>TODO</code>, <a href=/development/code_comments/>include a link to the relevant issue</a>.</p><p>Write comments that <a href=https://blog.codinghorror.com/code-tells-you-how-comments-tell-you-why/>explain why, not only what</a>
the code does.</p><p>Request maintainer reviews only when tests pass. If tests are failing, explain why in a comment.
Contact maintainers by email or Slack only for immediate requests.
In all other cases, adding them as a reviewer is sufficient.</p><h3 id=the-responsibility-of-the-reviewer>The responsibility of the reviewer</h3><p>Reviewers are responsible for reviewing the specifics of the chosen solution.</p><p>If unavailable within the
<a href=https://handbook.gitlab.com/handbook/engineering/workflow/code-review/#review-response-slo>Review-response SLO</a>,
inform the author, find a replacement using the
<a href=https://gitlab-org.gitlab.io/gitlab-roulette/>Review Workload Dashboard</a>, and assign them.</p><p>When confident the MR meets all
<a href=/development/contributing/merge_request_workflow/#contribution-acceptance-criteria>contribution acceptance criteria</a>:</p><ol><li>Select <strong>Approve</strong>.</li><li><code>@</code> mention the author to notify them.</li><li>Request a review from a maintainer with <a href=/development/code_review/#domain-experts>domain expertise</a>, or follow the
<a href=/development/code_review/#reviewer-roulette>Reviewer roulette</a> suggestion.</li></ol><h3 id=the-responsibility-of-the-maintainer>The responsibility of the maintainer</h3><p>Maintainers are responsible for the overall health, quality, and consistency of
the GitLab codebase.
Their reviews focus on architecture, code organization, separation of concerns, tests,
DRYness, consistency, and readability.</p><p>Maintainers are the DRI for ensuring MRs reasonably meet
<a href=/development/contributing/merge_request_workflow/#contribution-acceptance-criteria>acceptance criteria</a>.</p><p>A maintainer makes sound judgements when evaluating the impact of an MR.
If a maintainer feels that an MR is not able to merged, it is their responsibility to say so.
The maintainer is also the expert adviser who knows when to pull in others for a
second opinion.</p><p>When a maintainer approves an MR, they are taking responsibility alongside the author.
This means that when there is a production incident, the maintainer may get
paged to help resolve issues.</p><p>Certain merge requests may target a stable branch. For an overview of how to handle these requests,
see the <a href=https://gitlab.com/gitlab-org/release/docs/-/blob/master/general/patch/engineers.md>patch release runbook</a>.</p><h2 id=best-practices>Best practices</h2><h3 id=domain-experts>Domain experts</h3><p>Domain experts are team members who have substantial experience with a specific technology,
product feature, or area of the codebase. Team members are encouraged to self-identify as
domain experts and add it to their
<a href=https://handbook.gitlab.com/handbook/engineering/workflow/code-review/#how-to-self-identify-as-a-domain-expert>team profiles</a>.</p><p>When self-identifying as a domain expert, it is recommended to assign the MR changing the <code>.yml</code> file to be merged by an already established Domain Expert or a corresponding Engineering Manager.</p><p>We make the following assumption with regards to automatically being considered a domain expert:</p><ul><li>Team members working in a specific stage/group (for example, create: source code) are considered domain experts for that area of the app they work on.</li><li>Team members working on a specific feature (for example, search) are considered domain experts for that feature.</li></ul><p>We default to assigning reviews to team members with domain expertise for code reviews. UX reviews default to the recommended reviewer from the Review Roulette. Due to designer capacity limits, areas not supported by a Product Designer will no longer require a UX review unless it is a community contribution.
When a suitable <a href=/development/code_review/#domain-experts>domain expert</a> isn&rsquo;t available, you can choose any team member to review the MR, or follow the <a href=/development/code_review/#reviewer-roulette>Reviewer roulette</a> recommendation (see above for UX reviews). Double check if the person is OOO before assigning them.</p><p>To find a domain expert:</p><ul><li>In the Merge Request approvals widget, select <a href=/user/project/merge_requests/approvals/rules/#eligible-approvers>View eligible approvers</a>.
This widget shows recommended and required approvals per area of the codebase.
These rules are defined in <a href=/user/project/merge_requests/approvals/rules/#code-owners-as-approvers>Code Owners</a>.</li><li>View the list of team members who work in the <a href=https://handbook.gitlab.com/handbook/product/categories/#devops-stages>stage or group</a> related to the merge request.</li><li>View team members&rsquo; domain expertise on the <a href=https://handbook.gitlab.com/handbook/engineering/projects/>engineering projects</a> page or on the <a href=https://about.gitlab.com/company/team/>GitLab team page</a>. Domains are self-identified, so use your judgment to map the changes on your merge request to a domain.</li><li>Look for team members who have contributed to the files in the merge request. View the logs by running <code>git log &lt;file></code>.</li><li>Look for team members who have reviewed the files. You can find the relevant merge request by:<ol><li>Getting the commit SHA by using <code>git log &lt;file></code>.</li><li>Navigating to <code>https://gitlab.com/gitlab-org/gitlab/-/commit/&lt;SHA></code>.</li><li>Selecting the related merge request shown for the commit.</li></ol></li></ul><h3 id=reviewer-roulette>Reviewer roulette</h3><div class="alert alert-type-note gl-rounded-lg"><div class=alert-icon></div><div class=gl-min-w-0><p><a href=https://gitlab-org.gitlab.io/gitlab-roulette/>Reviewer roulette</a> is an internal tool for
GitLab.com, not available on customer installations.</p></div></div><p>The <a href=/development/dangerbot/>Danger bot</a> picks a reviewer and maintainer for each codebase area your MR
touches. Override the suggestion if you know a better fit.</p><p>The roulette skips people whose status contains <code>OOO</code>, <code>PTO</code>, <code>Parental Leave</code>, <code>Friends and Family</code>, or <code>Conference</code>, or who are at review capacity (set via a number status emoji: 2️⃣–5️⃣).</p><h3 id=acceptance-checklist>Acceptance checklist</h3><p>This checklist encourages the authors, reviewers, and maintainers of merge requests (MRs) to confirm changes were analyzed for high-impact risks to quality, performance, reliability, security, observability, and maintainability.</p><p>Using checklists improves quality in software engineering. This checklist is a straightforward tool to support and bolster the skills of contributors to the GitLab codebase.</p><h4 id=quality>Quality</h4><p>For further quality guidelines, see <a href=https://handbook.gitlab.com/handbook/engineering/testing/>testing</a>.</p><ol><li>You have self-reviewed this MR per <a href=/development/code_review/>code review guidelines</a>.</li><li>The code follows the <a href=/development/software_design/>software design guidelines</a>.</li><li>Ensure <a href=/development/testing_guide/>automated tests</a> exist following the <a href=/development/testing_guide/testing_levels/>testing pyramid</a>. Add missing tests or create an issue documenting testing gaps.</li><li>You have considered the technical impacts on GitLab.com, Dedicated and self-managed.</li><li>You have considered the impact of this change on the frontend, backend, and database portions of the system where appropriate and applied the <code>~ux</code>, <code>~frontend</code>, <code>~backend</code>, and <code>~database</code> labels accordingly.</li><li>You have tested this MR in <a href=/install/requirements/#supported-web-browsers>all supported browsers</a>, or determined that this testing is not needed.</li><li>You have confirmed that this change is <a href=/development/multi_version_compatibility/>backwards compatible across updates</a>, or you have decided that this does not apply.</li><li>You have properly separated <a href=/development/ee_features/>EE content</a> (if any) from FOSS. Consider <a href=/development/ee_features/#run-ci-pipelines-in-a-foss-context>running the CI pipelines in a FOSS context</a>.</li><li>You have considered that existing data may be surprisingly varied. For example, if adding a new model validation, consider making it optional on existing data.</li><li>You have fixed flaky tests related to this MR, or have explained why they can be ignored. Flaky tests have error <code>Flaky test '&lt;path/to/test>' was found in the list of files changed by this MR.</code> but can be in jobs that pass with warnings.</li></ol><h4 id=performance-reliability-and-availability>Performance, reliability, and availability</h4><ol><li>You are confident that this MR does not harm performance, or you have asked a reviewer to help assess the performance impact. (<a href=/development/merge_request_concepts/performance/>Merge request performance guidelines</a>)</li><li>You have added <a href=/development/database_review/#required>information for database reviewers in the MR description</a>, or you have decided that it is unnecessary.<ul><li><a href=/development/database_review/>Does this MR have database-related changes?</a></li></ul></li><li>You have considered the availability and reliability risks of this change.</li><li>You have considered the scalability risk based on future predicted growth.</li><li>You have considered the performance, reliability, and availability impacts of this change on large customers who may have significantly more data than the average customer.</li><li>You have considered the performance, reliability, and availability impacts of this change on customers who may run GitLab on the <a href=/install/requirements/>minimum system</a>.</li><li>You are confident that this change is compatible with the <a href=/development/cells/>Cells architecture</a>. For more information, see
<a href=/development/cells/#cells-development-principles>Cells development principles</a>.</li></ol><h4 id=observability-instrumentation>Observability instrumentation</h4><ol><li>You have included enough instrumentation to facilitate debugging and proactive performance improvements through observability.
See <a href=https://gitlab.com/gitlab-org/gitlab/-/issues/346124#expectations>example</a> of adding feature flags, logging, and instrumentation.</li></ol><h4 id=documentation>Documentation</h4><ol><li>You have included changelog trailers, or you have decided that they are not needed.<ul><li><a href=/development/changelog/#what-warrants-a-changelog-entry>Does this MR need a changelog?</a></li></ul></li><li>You have added/updated documentation or decided that documentation changes are unnecessary for this MR.<ul><li><a href=/development/documentation/workflow/#documentation-for-a-product-change>Is documentation required?</a></li></ul></li></ol><h4 id=security>Security</h4><ol><li>You have confirmed that if this MR contains changes to processing or storing of credentials or tokens, authorization, and authentication methods, or other items described in <a href=https://handbook.gitlab.com/handbook/security/product-security/security-platforms-architecture/application-security/appsec-reviews/#what-should-be-reviewed>the security review guidelines</a>, you have added the <code>~security</code> label and you have <code>@</code>-mentioned <code>@gitlab-com/gl-security/appsec</code>.</li><li>You have reviewed the documentation regarding <a href=https://handbook.gitlab.com/handbook/security/product-security/security-platforms-architecture/application-security/appsec-reviews/#internal-application-security-reviews>internal application security reviews</a> for <strong>when</strong> and <strong>how</strong> to request a security review and requested a security review if this is warranted for this change.</li><li>If there are security scan results that are blocking the MR (due to the <a href=https://gitlab.com/gitlab-com/gl-security/security-policies>merge request approval policies</a>):<ul><li>For true positive findings, they should be corrected before the merge request is merged. This will remove the AppSec approval required by the merge request approval policy.</li><li>For false positive findings, something that should be discussed for risk acceptance, or anything questionable, ping <code>@gitlab-com/gl-security/appsec</code>.</li></ul></li></ol><h4 id=deployment>Deployment</h4><ol><li>You have considered using a feature flag for this change because the change may be high risk.</li><li>If you are using a feature flag, you plan to test the change in staging before you test it in production, and you have considered rolling it out to a subset of production customers before rolling it out to all customers.<ul><li><a href=https://handbook.gitlab.com/handbook/product-development/how-we-work/product-development-flow/feature-flag-lifecycle/#when-to-use-feature-flags>When to use a feature flag</a></li></ul></li><li>You have informed the Infrastructure department of a default setting or new setting change per <a href=/development/contributing/merge_request_workflow/#definition-of-done>definition of done</a>, or decided that this is unnecessary.</li></ol><h4 id=compliance>Compliance</h4><ol><li>You have confirmed that the correct <a href=/development/labels/>MR type label</a> has been applied.</li></ol><h3 id=participating-in-code-review>Participating in code review</h3><ul><li>Be kind.</li><li>Accept that many programming decisions are opinions. Discuss trade-offs and resolve quickly.</li><li>Ask questions. Make suggestions, not demands.</li><li>Be explicit. People don&rsquo;t always understand your intentions online.</li><li>Be humble. Consider a one-on-one call for lengthy misunderstandings and post a follow-up summary.</li><li>Mention the person directly when a comment is addressed specifically to them.</li><li>Read through the entire diff before your first push. Check for unrelated changes and debug code.</li><li>Write a detailed description per the
<a href=/development/contributing/merge_request_workflow/#merge-request-guidelines-for-contributors>merge request guidelines</a>.</li><li>Don&rsquo;t take feedback personally. The review is of the code and its impact on production systems.</li><li>Explain why the code exists, not just what it does.</li><li>Try to respond to every comment. Only resolve threads you have fully addressed. If a comment can be
addressed in a follow-up issue, work with the maintainer on a path forward.</li><li>Re-request review once you are ready for another round.</li><li>Address all GitLab Duo review comments before requesting a review from human reviewers.</li></ul><h3 id=for-authors-getting-changes-merged-faster>For authors: getting changes merged faster</h3><ol><li>Follow best practices: write clear descriptions, add screenshots and validation steps, address
<code>dangerbot</code> comments, and complete the <a href=/development/code_review/#acceptance-checklist>acceptance checklist</a>.</li><li>Follow GitLab patterns. Long discussions delay merging. Consider following the documented
approach, then open a separate MR to propose changes to best practices.</li><li>Keep MRs small. Around 200 lines is a good target.<ul><li>Smaller MRs are reviewed faster and have fewer blocking discussions.</li><li>Use <a href=/user/project/merge_requests/stacked_diffs/>stacked diffs</a> for sequential MRs.</li><li>Split changes so only one maintainer is required per MR (for example, ship database changes
before the feature).</li><li>UI with mocked data must be behind a <a href=/development/feature_flags/>feature flag</a>.</li></ul></li><li>Minimize the number of reviewers. A database reviewer can also review backend; a fullstack
engineer can cover frontend and backend.</li><li>Know your maintainers and assign domain experts. Maintainers prioritize MRs in areas they know
well.</li></ol><h3 id=merging-a-merge-request>Merging a merge request</h3><p>Before merging:</p><ul><li>Set the milestone.</li><li>Confirm the correct <a href=/development/labels/#type-labels>MR type label</a> is applied.</li><li>Resolve warnings and errors from Danger bot, code quality, and other reports. Post a comment if
merging with any failed job.</li></ul><p>At least one maintainer must approve before merging. Authors and people who add commits cannot
approve their own MR.</p><p>If the final approver did not set auto-merge, the MR author may merge their own MR if all required
approvals are in place and they have merge rights. This aligns with the GitLab
<a href=https://handbook.gitlab.com/handbook/values/#bias-for-action>bias for action</a> value.</p><p>When ready to merge:</p><div class="alert alert-type-warning gl-rounded-lg"><div class=alert-icon></div><div class=gl-min-w-0><p>If the merge request is from a fork, also check the
<a href=/development/code_review/#community-contributions>guidelines for community contributions</a>.</p></div></div><ul><li>Use <a href=/user/project/merge_requests/squash_and_merge/>Squash and merge</a> only if the author
set it or the commit history is messy.</li><li>In the <strong>Pipelines</strong> tab, select <strong>Run pipeline</strong>, then enable <strong>Auto-merge</strong> on the
<strong>Overview</strong> tab.<ul><li>Do not merge when
<a href=https://handbook.gitlab.com/handbook/engineering/workflow/#broken-master>the default branch is broken</a>,
except in
<a href=https://handbook.gitlab.com/handbook/engineering/workflow/#criteria-for-merging-during-broken-master>specific cases</a>.</li><li>Start a new pipeline if the latest one was created before approval and the MR has backend
changes.</li><li>You may skip a new pipeline if the latest merged results pipeline was created less than 16
hours ago (72 hours for stable branches).</li></ul></li></ul><h3 id=community-contributions>Community contributions</h3><div class="alert alert-type-warning gl-rounded-lg"><div class=alert-icon></div><div class=gl-min-w-0><p><strong>Review all changes thoroughly for malicious code before starting a
<a href=/ci/pipelines/merge_request_pipelines/#run-pipelines-in-the-parent-project>merged results pipeline</a>.</strong></p></div></div><p>When reviewing community MRs:</p><ul><li>Scrutinize new dependencies (e.g. <code>Gemfile.lock</code>, <code>yarn.lock</code>). They could introduce malicious packages.</li><li>Review links and images, especially in documentation MRs.</li><li>When in doubt, ask <code>@gitlab-com/gl-security/appsec</code> to review before starting any pipeline.</li><li>Set the milestone only when the MR is likely to merge in the current milestone.</li></ul><h4 id=taking-over-a-community-merge-request>Taking over a community merge request</h4><p>When an MR needs changes but the author is unresponsive or unable to finish:</p><ol><li>Comment that you (the merge request coach) are taking over.</li><li>Add the <code>~"coach will finish"</code> label.</li><li>Create a feature branch from main and merge their branch into it.</li><li>Open a new MR, link the community MR, and add the <code>~"Community contribution"</code> label.</li><li>Notify the contributor and follow the regular review process.</li></ol><h3 id=finding-the-right-balance>Finding the right balance</h3><p>Finding the right balance in how deeply to review requires sound judgement. Keep in mind:</p><ul><li>Finding bugs is important, but good design reduces future complexity.</li><li>Enforce <a href=/development/contributing/style_guides/>code style</a> through
<a href=https://handbook.gitlab.com/handbook/values/#cleanup-over-sign-off>automation</a> rather than
review comments.</li><li>For non-blocking suggestions, consider approving the MR before passing it back. This reduces
time-to-merge.</li><li>Distinguish between doing things right and doing things right now. For example, avoid requiring major
refactors in an urgent security fix.</li><li>Doing things well today is usually better than doing something perfectly
tomorrow.</li></ul><h2 id=troubleshooting-failing-pipelines>Troubleshooting failing pipelines</h2><ul><li><strong>Unrelated test failures</strong>: Check if the failure also happens on the default branch.
If so, wait for the broken master fix, then re-run the pipeline for the MR.</li><li><strong><code>danger-review</code> job failed</strong>: Check if your MR has more than 20 commits. If so, rebase and
squash. Otherwise, re-run the job.</li></ul><p>For help, comment <code>@gitlab-bot help</code> on the MR, or ask in the
<a href=https://discord.gg/gitlab>Community Discord</a> <code>contribute</code> channel.</p><h3 id=credits>Credits</h3><p>Based on the <a
