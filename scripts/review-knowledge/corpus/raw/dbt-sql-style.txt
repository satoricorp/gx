<h2 class="anchor anchorWithHideOnScrollNavbar_WYt5" id=fields-aggregations-and-grouping>Fields, aggregations, and grouping<a href=#fields-aggregations-and-grouping class=hash-link aria-label="Direct link to Fields, aggregations, and grouping" title="Direct link to Fields, aggregations, and grouping">​</a></h2>
<ul>
<li>🔙 Fields should be stated before aggregates and window functions.</li>
<li>🤏🏻 Aggregations should be executed as early as possible (on the smallest data set possible) before joining to another table to improve performance.</li>
<li>🔢 Ordering and grouping by a number (eg. group by 1, 2) is preferred over listing the column names (see <a href=https://www.getdbt.com/blog/write-better-sql-a-defense-of-group-by-1 target=_blank rel="noopener noreferrer">this classic rant</a> for why). Note that if you are grouping by more than a few columns, it may be worth revisiting your model design.</li>
</ul>
<h2 class="anchor anchorWithHideOnScrollNavbar_WYt5" id=joins>Joins<a href=#joins class=hash-link aria-label="Direct link to Joins" title="Direct link to Joins">​</a></h2>
<ul>
<li>👭🏻 Prefer <code>union all</code> to <code>union</code> unless you explicitly want to remove duplicates.</li>
<li>👭🏻 If joining two or more tables, <em>always</em> prefix your column names with the table name. If only selecting from one table, prefixes are not needed.</li>
<li>👭🏻 Be explicit about your join type (i.e. write <code>inner join</code> instead of <code>join</code>).</li>
<li>🥸 Avoid table aliases in join conditions (especially initialisms) — it's harder to understand what the table called "c" is as compared to "customers".</li>
<li>➡️ Always move left to right to make joins easy to reason about - <code>right joins</code> often indicate that you should change which table you select <code>from</code> and which one you <code>join</code> to.</li>
</ul>
<h2 class="anchor anchorWithHideOnScrollNavbar_WYt5" id=import-ctes>'Import' CTEs<a href=#import-ctes class=hash-link aria-label="Direct link to 'Import' CTEs" title="Direct link to 'Import' CTEs">​</a></h2>
<ul>
<li>🔝 All <code>{{ ref('...') }}</code> statements should be placed in CTEs at the top of the file.</li>
<li>📦 'Import' CTEs should be named after the table they are referencing.</li>
<li>🤏🏻 Limit the data scanned by CTEs as much as possible. Where possible, only select the columns you're actually using and use <code>where</code> clauses to filter out unneeded data.</li>

<h2 class="anchor anchorWithHideOnScrollNavbar_WYt5" id=functional-ctes>'Functional' CTEs<a href=#functional-ctes class=hash-link aria-label="Direct link to 'Functional' CTEs" title="Direct link to 'Functional' CTEs">​</a></h2>
<ul>
<li>☝🏻 Where performance permits, CTEs should perform a single, logical unit of work.</li>
<li>📖 CTE names should be as verbose as needed to convey what they do e.g. <code>events_joined_to_users</code> instead of <code>user_events</code> (this could be a good model name, but does not describe a specific function or transformation).</li>
<li>🌉 CTEs that are duplicated across models should be pulled out into their own intermediate models. Look out for chunks of repeated logic that should be refactored into their own model.</li>
<li>🔚 The last line of a model should be a <code>select *</code> from your final output CTE. This makes it easy to materialize and audit the output from different steps in the model as you're developing it. You just change the CTE referenced in the <code>select</code> statement to see the output from that step.</li>
</ul>
