<h2 id="run-the-checks" class="h1">Run the checks</h2>
<p>OpenSSF Scorecard can be used in a couple of different ways:</p>
<ol>
<li>Run automatically on code you own <strong>using the GitHub Action</strong></li>
<li>Run manually on your (or somebody else’s) project <strong>via the Command Line</strong></li>
</ol>

<h2 id="learn-more" class="h1">Learn more</h2>
<blockquote>
<p>We rely on Security Scorecards <em>[i.e., OpenSSF Scorecard]</em> to ensure we follow secure development best practices.</p>
</blockquote>
<div class="text-right"><cite>Appu Goundan, <a href="https://github.com/GoogleContainerTools/distroless">Distroless</a></cite></div>
<h3 id="the-problem"><a href="#the-problem" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>The problem</h3>
<p>By some estimates* 84% of all codebases have at least one vulnerability, with an average of 158 per codebase. The majority have been in the code for more than 2 years and have documented solutions available.</p>
<p>Even in large tech companies, the tedious process of reviewing code for vulnerabilities falls down the priority list, and there is little insight into known vulnerabilities and solutions that companies can draw on.</p>
<p>That’s where Security Scorecards <em>[i.e., OpenSSF Scorecard]</em> is helping. Its focus is to understand the security posture of a project and assess the risks that dependencies introduce.</p>
<p>*<a href="https://www.synopsys.com/software-integrity/resources/analyst-reports/open-source-security-risk-analysis.html?intcmp=sig-blog-ossra1" rel="nofollow noopener noreferrer" target="_blank">Open Source Security and Risk Analysis Report</a> (Synopsys, 2021)</p>
<br>
<h3 id="what-is-openssf-scorecard"><a href="#what-is-openssf-scorecard" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>What is OpenSSF Scorecard?</h3>
<h5 id="scorecard-assesses-open-source-projects-for-security-risks-through-a-series-of-automated-checks"><a href="#scorecard-assesses-open-source-projects-for-security-risks-through-a-series-of-automated-checks" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>Scorecard assesses open source projects for security risks through a series of automated checks.</h5>
<p>It was created by OSS developers to help improve the health of critical projects that the community depends on.</p>
<p>You can use it to proactively assess and make informed decisions about accepting security risks within your codebase. You can also use the tool to evaluate other projects and dependencies, and work with maintainers to improve codebases you might want to integrate.</p>
<p>Scorecard helps you enforce best practices that can guard against:</p>

<h3 id="how-it-works"><a href="#how-it-works" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>How it works</h3>
<p>Scorecard checks for vulnerabilities affecting different parts of the software supply chain including <strong>source code</strong>, <strong>build</strong>, <strong>dependencies</strong>, <strong>testing</strong>, and project <strong>maintenance</strong>.</p>
<p>Each automated check returns a <strong>score out of 10</strong> and a <strong>risk level</strong>. The risk level <strong>adds a weighting</strong> to the score, and this weighting is compiled into a single, <strong>aggregate score</strong>. This score helps give a sense of the overall security posture of a project.</p>
<p>Alongside the scores, the tool provides remediation prompts to help you <strong>fix problems</strong> and strengthen your development practices.</p>
<p><img alt="scale of risk" src="assets/diagram-risks.svg"></p>
<br>
<h3 id="the-checks"><a href="#the-checks" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>The checks</h3>
<h5 id="the-checks-collect-together-security-best-practises-and-industry-standards"><a href="#the-checks-collect-together-security-best-practises-and-industry-standards" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>The checks collect together security best practises and industry standards</h5>
<p>The riskiness of each vulnerability is based on how easy it is to exploit. For example if something can be exploited via a pull request, we consider that a high risk. There are currently 18 checks made across 3 themes: holistic security practises, source code risk assessment and build process risk assessment.</p>
<p>You can learn more about the scoring criteria, risks, and remediation suggestions for each check in the <a href="https://github.com/ossf/scorecard/blob/main/docs/checks.md" rel="nofollow noopener noreferrer" target="_blank">detailed documentation</a>.</p>

<h3 id="use-cases"><a href="#use-cases" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>Use cases</h3>
<h5 id="openssf-scorecard-reduces-the-effort-required-to-continually-evaluate-changing-packages-when-maintaining-a-projects-supply-chain"><a href="#openssf-scorecard-reduces-the-effort-required-to-continually-evaluate-changing-packages-when-maintaining-a-projects-supply-chain" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>OpenSSF Scorecard reduces the effort required to continually evaluate changing packages when maintaining a project’s supply chain</h5>
<h4 id="for-individual-maintainers"><a href="#for-individual-maintainers" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>For individual maintainers</h4>
<p>Scorecard is helpful as a pre-launch security checker for a new OSS project or to help to plan improvements to an existing one. If a project is well maintained, it’s more likely to be used by others instead of an alternative. It can also be used to check a new dependency being added to a project, so a maintainer can make an informed decision about the risk of doing so.</p>
<h4 id="for-an-organisation"><a href="#for-an-organisation" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>For an organisation</h4>
<p>Scorecard can be included in the continuous integration/continuous deployment processes using the GitHub action and run by default on pull requests.</p>
<h4 id="for-consumers"><a href="#for-consumers" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>For consumers</h4>
<p>Scorecard helps to make informed decisions about security risks and vulnerabilities. Using the public data, it is also possible to evaluate the security posture of over 1 million of the most used OSS projects.</p>
<br>
<h3 id="about-the-project-name"><a href="#about-the-project-name" aria-hidden="true" tabindex="-1" title="Link to Section"><span class="icon icon-link"></span></a>About the project name</h3>
<p>This project was initially called "Security Scorecards" but that form wasn't used consistently. In particular, the repo was named "scorecard" and so was the program. Over time people started referring to either form (singular and plural), with or without "Security", and the inconsitency became prevalent. To end this situation the decision was made to consolidate over the use of the singular form in keeping with the repo and program name, drop the "Security" part and use "OpenSSF" instead to ensure uniqueness. One should therefore refer to this project as "OpenSSF Scorecard" or "Scorecard" for short.</p>
