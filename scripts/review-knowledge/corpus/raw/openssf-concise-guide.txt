    <h1 class="post-title">Concise Guide for Developing More Secure Software</h1>
  </header>

  <div class="post-content">
    <p><em>by the <a href="https://openssf.org">Open Source Security Foundation (OpenSSF)</a> <a href="https://best.openssf.org/">Best Practices Working Group</a>, 2023-06-14</em></p>

<p>Here is a concise guide for all software developers for secure software development, building, and distribution. All tools or services listed are merely examples.</p>

<ol>
  <li><strong>Ensure all privileged developers use</strong> <a href="https://github.com/ossf/great-mfa-project/blob/main/guide/token-usage-guide.md#readme"><strong>multi-factor authentication (MFA) tokens</strong></a>. This includes those with commit or accept privileges. MFA hinders attackers from “taking over” these accounts.</li>
  <li><strong>Learn about secure software development.</strong> Take, e.g., the <a href="https://openssf.org/training/courses/">free OpenSSF course</a> or the hands-on <a href="https://www.securityknowledgeframework.org/">Security Knowledge Framework</a> course. <a href="https://safecode.org/wp-content/uploads/2018/03/SAFECode_Fundamental_Practices_for_Secure_Software_Development_March_2018.pdf">SAFECode’s Fundamental Practices</a> <a href="https://safecode.org/wp-content/uploads/2018/03/SAFECode_Fundamental_Practices_for_Secure_Software_Development_March_2018.pdf">for Secure Software Development</a> provides a helpful summary.</li>
  <li><strong>Use a combination of tools in your CI pipeline to detect vulnerabilities</strong>. See the <a href="https://github.com/ossf/wg-security-tooling/blob/main/guide.md#readme">OpenSSF guide to security tools</a>. Tools shouldn’t be the <em>only</em> mechanism, but they scale.</li>
  <li><strong>Evaluate software before selecting it as a direct dependency</strong>. Only add it if needed, evaluate it (see <a href="https://best.openssf.org/Concise-Guide-for-Evaluating-Open-Source-Software">Concise Guide for Evaluating Open Source Software</a>), double-check its name (to counter typosquatting), and ensure it’s retrieved from the correct repository.</li>
  <li><strong>Use package managers</strong>. Use package managers (system, language-level, and/or container-level) to automatically manage dependencies and enable rapid updates.</li>
  <li><strong>Implement automated tests</strong>. Include negative tests (tests that what shouldn’t happen doesn’t happen) and ensure the test suite is thorough enough to “ship if it passes the tests”.</li>
  <li><strong>Monitor known vulnerabilities in your software’s direct &amp; indirect dependencies</strong>. E.g., enable basic scanning via GitHub’s <a href="https://docs.github.com/en/code-security/dependabot/dependabot-security-updates/configuring-dependabot-security-updates">dependabot</a> or GitLab <a href="https://docs.gitlab.com/ee/user/application_security/dependency_scanning/">dependency scanning</a>. Many other third party Software Composition Analysis (SCA) tools are also available. Quickly update vulnerable dependencies.</li>
  <li><strong>Keep dependencies reasonably up-to-date</strong>. Otherwise, it’s hard to update for vulnerabilities.</li>
  <li><strong>Do not push secrets to a repository</strong>. Use tools to detect pushing secrets to a repository.</li>
  <li><strong>Review before accepting changes</strong>. Enforce this, e.g., using <a href="https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/defining-the-mergeability-of-pull-requests/about-protected-branches">GitHub</a> or <a href="https://docs.gitlab.com/ee/user/project/protected_branches.html">GitLab</a> protected branches or an equivalent <a href="https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets">GitHub ruleset</a>.</li>
  <li><strong>Prominently document how to report vulnerabilities &amp; prepare for them</strong>.
    <ul>
      <li>Use resources like the <a href="https://github.com/ossf/oss-vulnerability-guide">Guide to coordinated vulnerability disclosure</a>.</li>
      <li><a href="/Vendored-Dependencies-Guide.html">Explicitly disclose security issues affecting vendored dependencies</a>.</li>
      <li>Create a <a href="https://github.com/ossf/oss-vulnerability-guide/tree/main/templates/security_policies">security policy</a>. Provide contacts.</li>
    </ul>
  </li>
  <li><strong>Make it easy for your users to update</strong>. Implement stable APIs, e.g., support old names when new ones are added. Use semantic versioning. Have a deprecation process.</li>
  <li><strong>Sign your project’s important releases</strong>. Use standard tools and signing formats for your distribution. See the <a href="https://docs.sigstore.dev/quickstart/quickstart-cosign/">cosign tool</a> from the <a href="https://www.sigstore.dev/">sigstore project</a> to sign containers and other artifacts.</li>
  <li><a href="https://www.bestpractices.dev/"><strong>Earn an OpenSSF Best Practices badge</strong></a> for your open source project. At least earn “passing”. Plan and roadmap to eventually earn silver &amp; gold.</li>
  <li><strong>Improve your</strong> <a href="https://github.com/ossf/scorecard"><strong>OpenSSF Scorecards</strong></a> <strong>score (if OSS and on GitHub)</strong>. You can read the <a href="https://github.com/ossf/scorecard#scorecard-checks">Scorecards checks</a>. Use the <a href="https://github.com/ossf/allstar">Allstar</a> monitor.</li>
  <li><strong>Notify the community of vulnerabilities in your project.</strong> Publish security advisories with accurate &amp; precise information, e.g., what usage &amp; versions are vulnerable, mitigations, and fixed version(s). Get a CVE ID. On GitHub, <a href="https://docs.github.com/en/code-security/repository-security-advisories/creating-a-repository-security-advisory#creating-a-security-advisory">create your security advisory</a> &amp; <a href="https://docs.github.com/en/code-security/repository-security-advisories/about-github-security-advisories-for-repositories#cve-identification-numbers">request a CVE</a>.</li>
  <li><strong>Improve your</strong> <a href="https://slsa.dev/"><strong>Supply chain Levels for Software Artifacts (SLSA)</strong></a> <strong>level</strong>. This hardens the integrity of your build and distribution process against attacks.</li>
  <li><strong>Publish and consume a software bill of materials (SBOM)</strong>. This lets users verify inventory, id known vulnerabilities, &amp; id potential legal issues. Consider <a href="https://spdx.dev/"><strong>SPDX</strong></a> or <a href="https://cyclonedx.org/"><strong>CycloneDX</strong></a>. See our <a href="https://sbom-catalog.openssf.org/">SBOM-Everywhere catalog</a>.</li>
  <li><strong>Onboard your project into</strong> <a href="https://security.lfx.linuxfoundation.org/"><strong>LFX Security</strong></a> <strong>if you manage a Linux Foundation project</strong>.</li>
  <li><strong>Apply the</strong> <a href="https://github.com/cncf/tag-security/blob/main/supply-chain-security/supply-chain-security-paper/CNCF_SSCP_v1.pdf"><strong>CNCF Security TAG Software Supply Chain Best Practices guide</strong></a>.</li>
  <li><strong>Implement</strong> <a href="https://owasp.org/www-project-application-security-verification-standard/"><strong>ASVS</strong></a> <strong>and follow relevant</strong> <a href="https://cheatsheetseries.owasp.org/index.html"><strong>cheatsheets</strong></a>.</li>
  <li><strong>Apply SAFECode’s</strong> <a href="https://safecode.org/uncategorized/fundamental-practices-secure-software-development/"><strong>Fundamental Practices for Secure Software Development</strong></a>.</li>
  <li><strong>Complete a third-party security code review/audit</strong>. Expect this to be USD$50K or more.</li>
  <li><strong>Continuously improve</strong>. Improve scores, look for tips, &amp; apply as appropriate.</li>
  <li><strong>Manage succession</strong>. Have clear governance &amp; work to add active, trustworthy maintainer(s).</li>
  <li><strong>Prefer memory-safe languages</strong>. Many vulnerabilities involve memory safety. Where practical, use memory-safe programming languages (most are) and keep memory safety enabled. Otherwise, use mechanisms like compiler flags, extra tools, and peer review to reduce risk; see <a href="https://best.openssf.org/Compiler-Hardening-Guides/Compiler-Options-Hardening-Guide-for-C-and-C++">Compiler Options Hardening Guide for C and C++</a>.</li>
  <li><strong>If a source code (unbuilt) package is released, it should only include content from the version control system (VCS), and source package users should rebuild, if needed, to create production (built) package(s)</strong>. E.g., if autotools is used, if a source package is released it should <em>not</em> include a generated <code class="language-plaintext highlighter-rouge">configure</code> file, while recipients should ignore pre-generated files like <code class="language-plaintext highlighter-rouge">configure</code> and instead rebuild from source (e.g., with <code class="language-plaintext highlighter-rouge">autoreconf</code>). This eliminates a malware-hiding mechanism, as illustrated by an attack on <a href="https://access.redhat.com/security/cve/CVE-2024-3094">xz utils</a>.</li>
  <li><strong>Ensure production websites only load assets from your own domains</strong>. <em>Linking</em> to other domains is fine, but where practical, don’t directly load assets such as JavaScript, CSS, and media (including images) from domains you do not control. If you do, your site might be subverted if that other domain is subverted, so investigate the risks before doing so. See the <a href="https://blog.qualys.com/vulnerabilities-threat-research/2024/06/28/polyfill-io-supply-chain-attack">subverted polyfill.io revelation in 2024</a>.</li>
  <li><strong>Apply focused security guidelines</strong>. Consult focused <a href="https://openssf.org/resources/guides/">OpenSSF guides</a> as applicable, such as the
<a href="https://best.openssf.org/Compiler-Hardening-Guides/Compiler-Options-Hardening-Guide-for-C-and-C++">Compiler Options Hardening Guide for C and C++</a>,
<a href="https://github.com/ossf/package-manager-best-practices/blob/main/published/npm.md#readme">npm Best Practices Guide</a>, and the guide to <a href="https://best.openssf.org/Correctly-Using-Regular-Expressions">Correctly Using Regular Expressions for Secure Input Validation</a>.</li>
</ol>

<p>We welcome suggestions and updates! Please open an <a href="https://github.com/ossf/wg-best-practices-os-developers/issues/">issue</a> or post a <a href="https://github.com/ossf/wg-best-practices-os-developers/pulls">pull request</a>.</p>

  </div>
