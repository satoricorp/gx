Here we provide guidelines on the code style and code organization for projects that use Kotlin.</p><section class="chapter"><h2 id="configure-style-in-ide" data-toc="configure-style-in-ide">Configure style in IDE</h2><p id="-9es39t_11">Two most popular IDEs for Kotlin - <a href="https://www.jetbrains.com/idea/" id="-9es39t_14" data-external="true" rel="noopener noreferrer">IntelliJ IDEA</a> and <a href="https://developer.android.com/studio/" id="-9es39t_15" data-external="true" rel="noopener noreferrer">Android Studio</a> provide powerful support for code styling. You can configure them to automatically format your code in consistence with the given code style.</p><section class="chapter"><h3 id="apply-the-style-guide" data-toc="apply-the-style-guide">Apply the style guide</h3><ol class="list _decimal" id="-9es39t_16" type="1"><li class="list__item" id="-9es39t_17"><p id="-9es39t_20">Go to <span class="control" id="-9es39t_21">Settings/Preferences | Editor | Code Style | Kotlin</span>.</p></li><li class="list__item" id="-9es39t_18"><p id="-9es39t_22">Click <span class="control" id="-9es39t_23">Set from...</span>.</p></li><li class="list__item" id="-9es39t_19"><p id="-9es39t_24">Select <span class="control" id="-9es39t_25">Kotlin style guide</span>.</p></li></ol></section><section class="chapter"><h3 id="verify-that-your-code-follows-the-style-guide" data-toc="verify-that-your-code-follows-the-style-guide">Verify that your code follows the style guide</h3><ol class="list _decimal" id="-9es39t_26" type="1"><li class="list__item" id="-9es39t_28"><p id="-9es39t_30">Go to <span class="control" id="-9es39t_31">Settings/Preferences | Editor | Inspections | General</span>.</p></li><li class="list__item" id="-9es39t_29"><p id="-9es39t_32">Switch on <span class="control" id="-9es39t_33">Incorrect formatting</span> inspection. Additional inspections that verify other issues described in the style guide (such as naming conventions) are enabled by default.</p></li></ol><p id="-9es39t_27">For more information, see the <a href="code-style-migration-guide.html" id="-9es39t_34">Migrate to Kotlin code style with IntelliJ IDEA</a> guide.</p></section></section><section class="chapter"><h2 id="source-code-organization" data-toc="source-code-organization">Source code organization</h2><section class="chapter"><h3 id="directory-structure" data-toc="directory-structure">Directory structure</h3><p id="-9es39t_41">In pure Kotlin projects, the recommended directory structure follows the package structure with the common root package omitted. For example, if all the code in the project is in the <code class="code" id="-9es39t_43">org.example.kotlin</code> package and its subpackages, files with the <code class="code" id="-9es39t_44">org.example.kotlin</code> package should be placed directly under the source root, and files in <code class="code" id="-9es39t_45">org.example.kotlin.network.socket</code> should be in the <code class="code" id="-9es39t_46">network/socket</code> subdirectory of the source root.</p><aside class="prompt" data-type="note" data-title="" id="-9es39t_42"><p id="-9es39t_47">On JVM: In projects where Kotlin is used together with Java, Kotlin source files should reside in the same source root as the Java source files, and follow the same directory structure: each file should be stored in the directory corresponding to each package statement.</p></aside></section><section class="chapter"><h3 id="source-file-names" data-toc="source-file-names">Source file names</h3><p id="-9es39t_48">If a Kotlin file contains a single class or interface (potentially with related top-level declarations), its name should be the same as the name of the class, with the <code class="code" id="-9es39t_51">.kt</code> extension appended. It applies to all types of classes and interfaces. If a file contains multiple classes, or only top-level declarations, choose a name describing what the file contains, and name the file accordingly. Use <a href="https://en.wikipedia.org/wiki/Camel_case" id="-9es39t_52" data-external="true" rel="noopener noreferrer">upper camel case</a>, where the first letter of each word is capitalized. For example, <code class="code" id="-9es39t_53">ProcessDeclarations.kt</code>.</p><p id="-9es39t_49">The name of the file should describe what the code in the file does. Therefore, you should avoid using meaningless words such as <code class="code" id="-9es39t_54">Util</code> in file names.</p><section class="chapter"><h4 id="multiplatform-projects" data-toc="multiplatform-projects">Multiplatform projects</h4><p id="-9es39t_55">In multiplatform projects, files with top-level declarations in platform-specific source sets should have a suffix associated with the name of the source set. For example:</p><ul class="list _bullet" id="-9es39t_56"><li class="list__item" id="-9es39t_59"><p id="-9es39t_62"><span class="control" id="-9es39t_63">jvm</span>Main/kotlin/Platform. <span class="control" id="-9es39t_64">jvm</span> .kt</p></li><li class="list__item" id="-9es39t_60"><p id="-9es39t_65"><span class="control" id="-9es39t_66">android</span>Main/kotlin/Platform. <span class="control" id="-9es39t_67">android</span> .kt</p></li><li class="list__item" id="-9es39t_61"><p id="-9es39t_68"><span class="control" id="-9es39t_69">ios</span>Main/kotlin/Platform. <span class="control" id="-9es39t_70">ios</span> .kt</p></li></ul><p id="-9es39t_57">As for the common source set, files with top-level declarations should not have a suffix. For example, <code class="code" id="-9es39t_71">commonMain/kotlin/Platform.kt</code>.</p><section class="chapter"><div class="collapse"><div class="collapse__title"><h5 id="technical-details" data-toc="technical-details">Technical details</h5></div><div class="collapse__content"><p id="-9es39t_72">We recommend following this file naming scheme in multiplatform projects due to JVM limitations: it doesn't allow top-level members (functions, properties).</p><p id="-9es39t_73">To work around this, the Kotlin JVM compiler creates wrapper classes (so-called &quot;file facades&quot;) that contain top-level member declarations. File facades have an internal name derived from the file name.</p><p id="-9es39t_74">In turn, JVM doesn't allow several classes with the same fully qualified name (FQN). This might lead to situations when a Kotlin project cannot be compiled to JVM:</p><div class="code-block" data-lang="none">
root
|- commonMain/kotlin/myPackage/Platform.kt // contains 'fun count() { }'
|- jvmMain/kotlin/myPackage/Platform.kt // contains 'fun multiply() { }'
</div><p id="-9es39t_76">Here both <code class="code" id="-9es39t_79">Platform.kt</code> files are in the same package, so the Kotlin JVM compiler produces two file facades, both of which have FQN <code class="code" id="-9es39t_80">myPackage.PlatformKt</code>. This produces the &quot;Duplicate JVM classes&quot; error.</p><p id="-9es39t_77">The simplest way to avoid that is renaming one of the files according to the guideline above. This naming scheme helps avoid clashes while retaining code readability.</p><aside class="prompt" data-type="tip" data-title="" id="-9es39t_78"><p id="-9es39t_81">There are two scenarios where these recommendations may seem redundant, but we still advise to follow them:</p><ul class="list _bullet" id="-9es39t_82"><li class="list__item" id="-9es39t_83"><p id="-9es39t_85">Non-JVM platforms don't have issues with duplicating file facades. However, this naming scheme can help you keep file naming consistent.</p></li><li class="list__item" id="-9es39t_84"><p id="-9es39t_86">On JVM, if source files don't have top-level declarations, the file facades aren't generated, and you won't face naming clashes.</p><p id="-9es39t_87">However, this naming scheme can help you avoid situations when a simple refactoring or an addition could include a top-level function and result in the same &quot;Duplicate JVM classes&quot; error.</p></li></ul></aside></div></div></section></section></section><section class="chapter"><h3 id="source-file-organization" data-toc="source-file-organization">Source file organization</h3><p id="-9es39t_88">Placing multiple declarations (classes, top-level functions or properties) in the same Kotlin source file is encouraged as long as these declarations are closely related to each other semantically, and the file size remains reasonable (not exceeding a few hundred lines).</p><p id="-9es39t_89">In particular, when defining extension functions for a class which are relevant for all clients of this class, put them in the same file with the class itself. When defining extension functions that make sense only for a specific client, put them next to the code of that client. Avoid creating files just to hold all extensions of some class.</p></section><section class="chapter"><h3 id="class-layout" data-toc="class-layout">Class layout</h3><p id="-9es39t_90">The contents of a class should go in the following order:</p><ol class="list _decimal" id="-9es39t_91" type="1"><li class="list__item" id="-9es39t_94"><p id="-9es39t_98">Property declarations and initializer blocks</p></li><li class="list__item" id="-9es39t_95"><p id="-9es39t_99">Secondary constructors</p></li><li class="list__item" id="-9es39t_96"><p id="-9es39t_100">Method declarations</p></li><li class="list__item" id="-9es39t_97"><p id="-9es39t_101">Companion object</p></li></ol><p id="-9es39t_92">Do not sort the method declarations alphabetically or by visibility, and do not separate regular methods from extension methods. Instead, put related stuff together, so that someone reading the class from top to bottom can follow the logic of what's happening. Choose an order (either higher-level stuff first, or vice versa) and stick to it.</p><p id="-9es39t_93">Put nested classes next to the code that uses those classes. If the classes are intended to be used externally and aren't referenced inside the class, put them in the end, after the companion object.</p></section><section class="chapter"><h3 id="interface-implementation-layout" data-toc="interface-implementation-layout">Interface implementation layout</h3><p id="-9es39t_102">When implementing an interface, keep the implementing members in the same order as members of the interface (if necessary, interspersed with additional private methods used for the implementation).</p></section><section class="chapter"><h3 id="overload-layout" data-toc="overload-layout">Overload layout</h3><p id="-9es39t_103">Always put overloads next to each other in a class.</p></section></section><section class="chapter"><h2 id="naming-rules" data-toc="naming-rules">Naming rules</h2><p id="-9es39t_104">Package and class naming rules in Kotlin are quite simple:</p><ul class="list _bullet" id="-9es39t_105"><li class="list__item" id="-9es39t_113"><p id="-9es39t_115">Names of packages are always lowercase and do not use underscores (<code class="code" id="-9es39t_116">org.example.project</code>). Using multi-word names is generally discouraged, but if you do need to use multiple words, you can either just concatenate them together or use camel case (<code class="code" id="-9es39t_117">org.example.myProject</code>).</p></li><li class="list__item" id="-9es39t_114"><p id="-9es39t_118">Names of classes and objects use upper camel case:</p></li></ul><div class="code-block" data-lang="kotlin">
open class DeclarationProcessor { /*...*/ }

object EmptyDeclarationProcessor : DeclarationProcessor() { /*...*/ }
</div><section class="chapter"><h3 id="function-names" data-toc="function-names">Function names</h3><p id="-9es39t_119">Names of functions, properties, and local variables start with a lowercase letter and use camel case without underscores:</p><div class="code-block" data-lang="kotlin">
fun processDeclarations() { /*...*/ }
var declarationCount = 1
</div></section><section class="chapter"><h3 id="names-for-class-like-functions" data-toc="names-for-class-like-functions">Names for class-like functions</h3><p id="-9es39t_121">There are two exceptions where function names should follow class-naming convention instead. Functions of this kind are usually defined at the top level.</p><ul class="list _bullet" id="-9es39t_122"><li class="list__item" id="-9es39t_123"><p id="-9es39t_125">Factory functions that create class instances can have the same name as the abstract return type:</p><div class="code-block" data-lang="kotlin">
interface Foo { /*...*/ }

class FooImpl : Foo { /*...*/ }

fun Foo(): Foo { return FooImpl() }
</div></li><li class="list__item" id="-9es39t_124"><p id="-9es39t_127"><code class="code" id="-9es39t_129">@Composable</code> functions that return <code class="code" id="-9es39t_130">Unit</code>:</p><div class="code-block" data-lang="kotlin">
@Composable fun TabHeader { /*...*/ }
</div></li></ul></section><section class="chapter"><h3 id="names-for-test-methods" data-toc="names-for-test-methods">Names for test methods</h3><p id="-9es39t_131">In tests (and <span class="control" id="-9es39t_133">only</span> in tests), you can use method names with spaces enclosed in backticks. Note that such method names are only supported by Android runtime from API level 30. Underscores in method names are also allowed in test code.</p><div class="code-block" data-lang="kotlin">
class MyTestCase {
    @Test fun `ensure everything works`() { /*...*/ }

    @Test fun ensureEverythingWorks_onAndroid() { /*...*/ }
}
</div></section><section class="chapter"><h3 id="property-names" data-toc="property-names">Property names</h3><p id="-9es39t_134">Names of constants (properties marked with <code class="code" id="-9es39t_141">const</code>, or top-level or object <code class="code" id="-9es39t_142">val</code> properties with no custom <code class="code" id="-9es39t_143">get</code> function that hold deeply immutable data) should use all uppercase, underscore-separated names following the <a href="https://en.wikipedia.org/wiki/Snake_case" id="-9es39t_144" data-external="true" rel="noopener noreferrer">screaming snake case</a> convention:</p><div class="code-block" data-lang="kotlin">
const val MAX_COUNT = 8
val USER_NAME_FIELD = &quot;UserName&quot;
</div><p id="-9es39t_136">Names of top-level or object properties which hold objects with behavior or mutable data should use camel case names:</p><div class="code-block" data-lang="kotlin">
val mutableCollection: MutableSet&lt;String&gt; = HashSet()
</div><p id="-9es39t_138">Names of properties holding references to singleton objects can use the same naming style as <code class="code" id="-9es39t_145">object</code> declarations:</p><div class="code-block" data-lang="kotlin">
val PersonComparator: Comparator&lt;Person&gt; = /*...*/
</div><p id="-9es39t_140">For enum constants, it's OK to use either all uppercase, underscore-separated (<a href="https://en.wikipedia.org/wiki/Snake_case" id="-9es39t_146" data-external="true" rel="noopener noreferrer">screaming snake case</a>) names (<code class="code" id="-9es39t_147">enum class Color { RED, GREEN }</code>) or upper camel case names, depending on the usage.</p></section><section class="chapter"><h3 id="names-for-backing-properties" data-toc="names-for-backing-properties">Names for backing properties</h3><p id="-9es39t_148">If a class has two properties which are conceptually the same but one is part of a public API and another is an implementation detail, use an underscore as the prefix for the name of the private property:</p><div class="code-block" data-lang="kotlin">
class C {
    private val _elementList = mutableListOf&lt;Element&gt;()

    val elementList: List&lt;Element&gt;
        get() = _elementList
}
</div></section><section class="chapter"><h3 id="choose-good-names" data-toc="choose-good-names">Choose good names</h3><p id="-9es39t_150">The name of a class is usually a noun or a noun phrase explaining what the class <span class="emphasis" id="-9es39t_155">is</span>: <code class="code" id="-9es39t_156">List</code>, <code class="code" id="-9es39t_157">PersonReader</code>.</p><p id="-9es39t_151">The name of a method is usually a verb or a verb phrase saying what the method <span class="emphasis" id="-9es39t_158">does</span>: <code class="code" id="-9es39t_159">close</code>, <code class="code" id="-9es39t_160">readPersons</code>. The name should also suggest if the method is mutating the object or returning a new one. For instance, <code class="code" id="-9es39t_161">sort</code> is sorting a collection in place, while <code class="code" id="-9es39t_162">sorted</code> is returning a sorted copy of the collection.</p><p id="-9es39t_152">The names should make it clear what the purpose of the entity is, so it's best to avoid using meaningless words (<code class="code" id="-9es39t_163">Manager</code>, <code class="code" id="-9es39t_164">Wrapper</code>) in names.</p><p id="-9es39t_153">When using an acronym as part of a declaration name, follow these rules:</p><ul class="list _bullet" id="-9es39t_154"><li class="list__item" id="-9es39t_165"><p id="-9es39t_167">For two-letter acronyms, use uppercase for both letters. For example, <code class="code" id="-9es39t_168">IOStream</code>.</p></li><li class="list__item" id="-9es39t_166"><p id="-9es39t_169">For acronyms longer than two letters, capitalize only the first letter. For example, <code class="code" id="-9es39t_170">XmlFormatter</code> or <code class="code" id="-9es39t_171">HttpInputStream</code>.</p></li></ul></section></section><section class="chapter"><h2 id="formatting" data-toc="formatting">Formatting</h2><section class="chapter"><h3 id="indentation" data-toc="indentation">Indentation</h3><p id="-9es39t_187">Use four spaces for indentation. Do not use tabs.</p><p id="-9es39t_188">For curly braces, put the opening brace at the end of the line where the construct begins, and the closing brace on a separate line aligned horizontally with the opening construct.</p><div class="code-block" data-lang="kotlin">
if (elements != null) {
    for (element in elements) {
        // ...
    }
}
</div><aside class="prompt" data-type="note" data-title="" id="-9es39t_190"><p id="-9es39t_191">In Kotlin, semicolons are optional, and therefore line breaks are significant. The language design assumes Java-style braces, and you may encounter surprising behavior if you try to use a different formatting style.</p></aside></section><section class="chapter"><h3 id="horizontal-whitespace" data-toc="horizontal-whitespace">Horizontal whitespace</h3><ul class="list _bullet" id="-9es39t_192"><li class="list__item" id="-9es39t_196"><p id="-9es39t_200">Put spaces around binary operators (<code class="code" id="-9es39t_201">a + b</code>). Exception: don't put spaces around the &quot;range to&quot; operator (<code class="code" id="-9es39t_202">0..i</code>).</p></li><li class="list__item" id="-9es39t_197"><p id="-9es39t_203">Do not put spaces around unary operators (<code class="code" id="-9es39t_204">a++</code>).</p></li><li class="list__item" id="-9es39t_198"><p id="-9es39t_205">Put spaces between control flow keywords (<code class="code" id="-9es39t_206">if</code>, <code class="code" id="-9es39t_207">when</code>, <code class="code" id="-9es39t_208">for</code>, and <code class="code" id="-9es39t_209">while</code>) and the corresponding opening parenthesis.</p></li><li class="list__item" id="-9es39t_199"><p id="-9es39t_210">Do not put a space before an opening parenthesis in a primary constructor declaration, method declaration or method call.</p></li></ul><div class="code-block" data-lang="kotlin">
class A(val x: Int)

fun foo(x: Int) { ... }

fun bar() {
    foo(1)
}
</div><ul class="list _bullet" id="-9es39t_194"><li class="list__item" id="-9es39t_211"><p id="-9es39t_217">Never put a space after <code class="code" id="-9es39t_218">(</code>, <code class="code" id="-9es39t_219">[</code>, or before <code class="code" id="-9es39t_220">]</code>, <code class="code" id="-9es39t_221">)</code>.</p></li><li class="list__item" id="-9es39t_212"><p id="-9es39t_222">Never put a space around <code class="code" id="-9es39t_223">.</code> or <code class="code" id="-9es39t_224">?.</code>: <code class="code" id="-9es39t_225">foo.bar().filter { it &gt; 2 }.joinToString()</code>, <code class="code" id="-9es39t_226">foo?.bar()</code>.</p></li><li class="list__item" id="-9es39t_213"><p id="-9es39t_227">Put a space after <code class="code" id="-9es39t_228">//</code>: <code class="code" id="-9es39t_229">// This is a comment</code>.</p></li><li class="list__item" id="-9es39t_214"><p id="-9es39t_230">Do not put spaces around angle brackets used to specify type parameters: <code class="code" id="-9es39t_231">class Map&lt;K, V&gt; { ... }</code>.</p></li><li class="list__item" id="-9es39t_215"><p id="-9es39t_232">Do not put spaces around <code class="code" id="-9es39t_233">::</code>: <code class="code" id="-9es39t_234">Foo::class</code>, <code class="code" id="-9es39t_235">String::length</code>.</p></li><li class="list__item" id="-9es39t_216"><p id="-9es39t_236">Do not put a space before <code class="code" id="-9es39t_237">?</code> used to mark a nullable type: <code class="code" id="-9es39t_238">String?</code>.</p></li></ul><p id="-9es39t_195">As a general rule, avoid horizontal alignment of any kind. Renaming an identifier to a name with a different length should not affect the formatting of either the declaration or any of the usages.</p></section><section class="chapter"><h3 id="colon" data-toc="colon">Colon</h3><p id="-9es39t_239">Put a space before <code class="code" id="-9es39t_244">:</code> in the following scenarios:</p><ul class="list _bullet" id="-9es39t_240"><li class="list__item" id="-9es39t_245"><p id="-9es39t_248">When it's used to separate a type and a supertype.</p></li><li class="list__item" id="-9es39t_246"><p id="-9es39t_249">When delegating to a superclass constructor or a different constructor of the same class.</p></li><li class="list__item" id="-9es39t_247"><p id="-9es39t_250">After the <code class="code" id="-9es39t_251">object</code> keyword.</p></li></ul><p id="-9es39t_241">Don't put a space before <code class="code" id="-9es39t_252">:</code> when it separates a declaration and its type.</p><p id="-9es39t_242">Always put a space after <code class="code" id="-9es39t_253">:</code>.</p><div class="code-block" data-lang="kotlin">
abstract class Foo&lt;out T : Any&gt; : IFoo {
    abstract fun foo(a: Int): T
}

class FooImpl : Foo() {
    constructor(x: String) : this(x) { /*...*/ }

    val x = object : IFoo { /*...*/ } 
}
</div></section><section class="chapter"><h3 id="class-headers" data-toc="class-headers">Class headers</h3><p id="-9es39t_254">Classes with a few primary constructor parameters can be written in a single line:</p><div class="code-block" data-lang="kotlin">
class Person(id: Int, name: String)
</div><p id="-9es39t_256">Classes with longer headers should be formatted so that each primary constructor parameter is in a separate line with indentation. Also, the closing parenthesis should be on a new line. If you use inheritance, the superclass constructor call, or the list of implemented interfaces should be located on the same line as the parenthesis:</p><div class="code-block" data-lang="kotlin">
class Person(
    id: Int,
    name: String,
    surname: String
) : Human(id, name) { /*...*/ }
</div><p id="-9es39t_258">For multiple interfaces, the superclass constructor call should be located first and then each interface should be located in a different line:</p><div class="code-block" data-lang="kotlin">
class Person(
    id: Int,
    name: String,
    surname: String
) : Human(id, name),
    KotlinMaker { /*...*/ }
</div><p id="-9es39t_260">For classes with a long supertype list, put a line break after the colon and align all supertype names horizontally:</p><div class="code-block" data-lang="kotlin">
class MyFavouriteVeryLongClassHolder :
    MyLongHolder&lt;MyFavouriteVeryLongClass&gt;(),
    SomeOtherInterface,
    AndAnotherOne {

    fun foo() { /*...*/ }
}
</div><p id="-9es39t_262">To clearly separate the class header and body when the class header is long, either put a blank line following the class header (as in the example above), or put the opening curly brace on a separate line:</p><div class="code-block" data-lang="kotlin">
class MyFavouriteVeryLongClassHolder :
    MyLongHolder&lt;MyFavouriteVeryLongClass&gt;(),
    SomeOtherInterface,
    AndAnotherOne 
{
    fun foo() { /*...*/ }
}
</div><p id="-9es39t_264">Use regular indent (four spaces) for constructor parameters. This ensures that properties declared in the primary constructor have the same indentation as properties declared in the body of a class.</p></section><section class="chapter"><h3 id="modifiers-order" data-toc="modifiers-order">Modifiers order</h3><p id="-9es39t_265">If a declaration has multiple modifiers, always put them in the following order:</p><div class="code-block" data-lang="kotlin">
public / protected / private / internal
expect / actual
final / open / abstract / sealed / const
external
override
lateinit
tailrec
vararg
suspend
inner
enum / annotation / fun // as a modifier in `fun interface` 
companion
inline / value
infix
operator
data
</div><p id="-9es39t_267">Place all annotations before modifiers:</p><div class="code-block" data-lang="kotlin">
@Named(&quot;Foo&quot;)
private val foo: Foo
</div><p id="-9es39t_269">Unless you're working on a library, omit redundant modifiers (for example, <code class="code" id="-9es39t_270">public</code>).</p></section><section class="chapter"><h3 id="annotations" data-toc="annotations">Annotations</h3><p id="-9es39t_271">Place annotations on separate lines before the declaration to which they are attached, and with the same indentation:</p><div class="code-block" data-lang="kotlin">
@Target(AnnotationTarget.PROPERTY)
annotation class JsonExclude
</div><p id="-9es39t_273">Annotations without arguments may be placed on the same line:</p><div class="code-block" data-lang="kotlin">
@JsonExclude @JvmField
var x: String
</div><p id="-9es39t_275">A single annotation without arguments may be placed on the same line as the corresponding declaration:</p><div class="code-block" data-lang="kotlin">
@Test fun foo() { /*...*/ }
</div></section><section class="chapter"><h3 id="file-annotations" data-toc="file-annotations">File annotations</h3><p id="-9es39t_277">File annotations are placed after the file comment (if any), before the <code class="code" id="-9es39t_279">package</code> statement, and are separated from <code class="code" id="-9es39t_280">package</code> with a blank line (to emphasize the fact that they target the file and not the package).</p><div class="code-block" data-lang="kotlin">
/** License, copyright and whatever */
@file:JvmName(&quot;FooBar&quot;)

package foo.bar
</div></section><section class="chapter"><h3 id="functions" data-toc="functions">Functions</h3><p id="-9es39t_281">If the function signature doesn't fit on a single line, use the following syntax:</p><div class="code-block" data-lang="kotlin">
fun longMethodName(
    argument: ArgumentType = defaultValue,
    argument2: AnotherArgumentType,
): ReturnType {
    // body
}
</div><p id="-9es39t_283">Use regular indent (four spaces) for function parameters. It helps ensure consistency with constructor parameters.</p><p id="-9es39t_284">Prefer using an expression body for functions with the body consisting of a single expression.</p><div class="code-block" data-lang="kotlin">
fun foo(): Int {     // bad
    return 1 
}

fun foo() = 1        // good
</div></section><section class="chapter"><h3 id="expression-bodies" data-toc="expression-bodies">Expression bodies</h3><p id="-9es39t_286">If the function has an expression body whose first line doesn't fit on the same line as the declaration, put the <code class="code" id="-9es39t_288">=</code> sign on the first line and indent the expression body by four spaces.</p><div class="code-block" data-lang="kotlin">
fun f(x: String, y: String, z: String) =
    veryLongFunctionCallWithManyWords(andLongParametersToo(), x, y, z)
</div></section><section class="chapter"><h3 id="properties" data-toc="properties">Properties</h3><p id="-9es39t_289">For very simple read-only properties, consider one-line formatting:</p><div class="code-block" data-lang="kotlin">
val isEmpty: Boolean get() = size == 0
</div><p id="-9es39t_291">For more complex properties, always put <code class="code" id="-9es39t_295">get</code> and <code class="code" id="-9es39t_296">set</code> keywords on separate lines:</p><div class="code-block" data-lang="kotlin">
val foo: String
    get() { /*...*/ }
</div><p id="-9es39t_293">For properties with an initializer, if the initializer is long, add a line break after the <code class="code" id="-9es39t_297">=</code> sign and indent the initializer by four spaces:</p><div class="code-block" data-lang="kotlin">
private val defaultCharset: Charset? =
    EncodingRegistry.getInstance().getDefaultCharsetForPropertiesFiles(file)
</div></section><section class="chapter"><h3 id="control-flow-statements" data-toc="control-flow-statements">Control flow statements</h3><p id="-9es39t_298">If the condition of an <code class="code" id="-9es39t_307">if</code> or <code class="code" id="-9es39t_308">when</code> statement is multiline, always use curly braces around the body of the statement. Indent each subsequent line of the condition by four spaces relative to the statement start. Put the closing parentheses of the condition together with the opening curly brace on a separate line:</p><div class="code-block" data-lang="kotlin">
if (!component.isSyncing &amp;&amp;
    !hasAnyKotlinRuntimeInScope(module)
) {
    return createKotlinNotConfiguredPanel(module)
}
</div><p id="-9es39t_300">This helps align the condition and statement bodies.</p><p id="-9es39t_301">Put the <code class="code" id="-9es39t_309">else</code>, <code class="code" id="-9es39t_310">catch</code>, <code class="code" id="-9es39t_311">finally</code> keywords, as well as the <code class="code" id="-9es39t_312">while</code> keyword of a <code class="code" id="-9es39t_313">do-while</code> loop, on the same line as the preceding curly brace:</p><div class="code-block" data-lang="kotlin">
if (condition) {
    // body
} else {
    // else part
}

try {
    // body
} finally {
    // cleanup
}
</div><p id="-9es39t_303">In a <code class="code" id="-9es39t_314">when</code> statement, if a branch is more than a single line, consider separating it from adjacent case blocks with a blank line:</p><div class="code-block" data-lang="kotlin">
private fun parsePropertyValue(propName: String, token: Token) {
    when (token) {
        is Token.ValueToken -&gt;
            callback.visitValue(propName, token.value)

        Token.LBRACE -&gt; { // ...
        }
    }
}
</div><p id="-9es39t_305">Put short branches on the same line as the condition, without braces.</p><div class="code-block" data-lang="kotlin">
when (foo) {
    true -&gt; bar() // good
    false -&gt; { baz() } // bad
}
</div></section><section class="chapter"><h3 id="method-calls" data-toc="method-calls">Method calls</h3><p id="-9es39t_315">In long argument lists, put a line break after the opening parenthesis. Indent arguments by four spaces. Group multiple closely related arguments on the same line.</p><div class="code-block" data-lang="kotlin">
drawSquare(
    x = 10, y = 10,
    width = 100, height = 100,
    fill = true
)
</div><p id="-9es39t_317">Put spaces around the <code class="code" id="-9es39t_318">=</code> sign separating the argument name and value.</p></section><section class="chapter"><h3 id="wrap-chained-calls" data-toc="wrap-chained-calls">Wrap chained calls</h3><p id="-9es39t_319">When wrapping chained calls, put the <code class="code" id="-9es39t_322">.</code> character or the <code class="code" id="-9es39t_323">?.</code> operator on the next line, with a single indent:</p><div class="code-block" data-lang="kotlin">
val anchor = owner
    ?.firstChild!!
    .siblings(forward = true)
    .dropWhile { it is PsiComment || it is PsiWhiteSpace }
</div><p id="-9es39t_321">The first call in the chain should usually have a line break before it, but it's OK to omit it if the code makes more sense that way.</p></section><section class="chapter"><h3 id="lambdas" data-toc="lambdas">Lambdas</h3><p id="-9es39t_324">In lambda expressions, spaces should be used around the curly braces, as well as around the arrow which separates the parameters from the body. If a call takes a single lambda, pass it outside parentheses whenever possible.</p><div class="code-block" data-lang="kotlin">
list.filter { it &gt; 10 }
</div><p id="-9es39t_326">If assigning a label for a lambda, do not put a space between the label and the opening curly brace:</p><div class="code-block" data-lang="kotlin">
fun foo() {
    ints.forEach lit@{
        // ...
    }
}
</div><p id="-9es39t_328">When declaring parameter names in a multiline lambda, put the names on the first line, followed by the arrow and the newline:</p><div class="code-block" data-lang="kotlin">
appendCommaSeparated(properties) { prop -&gt;
    val propertyValue = prop.get(obj)  // ...
}
</div><p id="-9es39t_330">If the parameter list is too long to fit on a line, put the arrow on a separate line:</p><div class="code-block" data-lang="kotlin">
foo {
    context: Context,
    environment: Env
    -&gt;
    context.configureEnv(environment)
}
</div></section><section class="chapter"><h3 id="trailing-commas" data-toc="trailing-commas">Trailing commas</h3><p id="-9es39t_332">A trailing comma is a comma symbol after the last item in a series of elements:</p><div class="code-block" data-lang="kotlin">
class Person(
    val firstName: String,
    val lastName: String,
    val age: Int, // trailing comma
)
</div><p id="-9es39t_334">Using trailing commas has several benefits:</p><ul class="list _bullet" id="-9es39t_335"><li class="list__item" id="-9es39t_350"><p id="-9es39t_353">It makes version-control diffs cleaner &ndash; as all the focus is on the changed value.</p></li><li class="list__item" id="-9es39t_351"><p id="-9es39t_354">It makes it easy to add and reorder elements &ndash; there is no need to add or delete the comma if you manipulate elements.</p></li><li class="list__item" id="-9es39t_352"><p id="-9es39t_355">It simplifies code generation, for example, for object initializers. The last element can also have a comma.</p></li></ul><p id="-9es39t_336">Trailing commas are entirely optional &ndash; your code will still work without them. The Kotlin style guide encourages the use of trailing commas at the declaration site and leaves it at your discretion for the call site.</p><p id="-9es39t_337">To enable trailing commas in the IntelliJ IDEA formatter, go to <span class="control" id="-9es39t_356">Settings/Preferences | Editor | Code Style | Kotlin</span>, open the <span class="control" id="-9es39t_357">Other</span> tab and select the <span class="control" id="-9es39t_358">Use trailing comma</span> option.</p><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="enumerations" data-toc="enumerations">Enumerations</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">
enum class Direction {
    NORTH,
    SOUTH,
    WEST,
    EAST, // trailing comma
}
</div></div></div></section><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="value-arguments" data-toc="value-arguments">Value arguments</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">
fun shift(x: Int, y: Int) { /*...*/ }
shift(
    25,
    20, // trailing comma
)
val colors = listOf(
    &quot;red&quot;,
    &quot;green&quot;,
    &quot;blue&quot;, // trailing comma
)
</div></div></div></section><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="class-properties-and-parameters" data-toc="class-properties-and-parameters">Class properties and parameters</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">
class Customer(
    val name: String,
    val lastName: String, // trailing comma
)
class Customer(
    val name: String,
    lastName: String, // trailing comma
)
</div></div></div></section><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="function-value-parameters" data-toc="function-value-parameters">Function value parameters</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">

    number: Int, 
    exponent: Int, // trailing comma
) { /*...*/ }

    x: Comparable&lt;Number&gt;,
    y: Iterable&lt;Number&gt;, // trailing comma
) {}

    vararg quantity: Int,
    description: String, // trailing comma
) {}
</div></div></div></section><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="parameters-with-optional-type-including-setters" data-toc="parameters-with-optional-type-including-setters">Parameters with optional type (including setters)</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">

    x,
    y,
    z, // trailing comma

    return x + y + x
}

</div></div></div></section><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="indexing-suffix" data-toc="indexing-suffix">Indexing suffix</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">
class Surface {
    operator fun get(x: Int, y: Int) = 2 * x + 4 * y - 10

    mySurface[
        xValue,
        yValue, // trailing comma
    ]
</div></div></div></section><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="parameters-in-lambdas" data-toc="parameters-in-lambdas">Parameters in lambdas</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">

    val x = {
            x: Comparable&lt;Number&gt;,
            y: Iterable&lt;Number&gt;, // trailing comma

        println(&quot;1&quot;)
    }
    println(x)
}
</div></div></div></section><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="when-entry" data-toc="when-entry">when entry</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">
fun isReferenceApplicable(myReference: KClass&lt;*&gt;) = when (myReference) {
    Comparable::class,
    Iterable::class,
    String::class, // trailing comma
        -&gt; true

}
</div></div></div></section><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="collection-literals-in-annotations" data-toc="collection-literals-in-annotations">Collection literals (in annotations)</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">

    &quot;serializer&quot;,
    &quot;balancer&quot;,
    &quot;database&quot;,

</div></div></div></section><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="type-arguments" data-toc="type-arguments">Type arguments</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">

    foo&lt;

</div></div></div></section><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="type-parameters" data-toc="type-parameters">Type parameters</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">

        MyKey,
        MyValue, // trailing comma
        &gt; {}
</div></div></div></section><section class="chapter"><div class="collapse"><div class="collapse__title"><h4 id="destructuring-declarations" data-toc="destructuring-declarations">Destructuring declarations</h4></div><div class="collapse__content"><div class="code-block" data-lang="kotlin">

    manufacturer,
    model,

    var meanValue: Int = 0

        _,

}
printMeanValue()
</div></div></div></section></section></section><section class="chapter"><h2 id="documentation-comments" data-toc="documentation-comments">Documentation comments</h2><p id="-9es39t_371">For longer documentation comments, place the opening <code class="code" id="-9es39t_377">/**</code> on a separate line and begin each subsequent line with an asterisk:</p><div class="code-block" data-lang="kotlin">
/**
 * This is a documentation comment
 * on multiple lines.
 */
</div><p id="-9es39t_373">Short comments can be placed on a single line:</p><div class="code-block" data-lang="kotlin">
/** This is a short documentation comment. */
</div><p id="-9es39t_375">Generally, avoid using <code class="code" id="-9es39t_378">@param</code> and <code class="code" id="-9es39t_379">@return</code> tags. Instead, incorporate the description of parameters and return values directly into the documentation comment, and add links to parameters wherever they are mentioned. Use <code class="code" id="-9es39t_380">@param</code> and <code class="code" id="-9es39t_381">@return</code> only when a lengthy description is required which doesn't fit into the flow of the main text.</p><div class="code-block" data-lang="kotlin">
// Avoid doing this:

/**
 * Returns the absolute value of the given number.
 * @param number The number to return the absolute value for.
 * @return The absolute value.
 */
fun abs(number: Int): Int { /*...*/ }

// Do this instead:

/**
 * Returns the absolute value of the given [number].
 */
fun abs(number: Int): Int { /*...*/ }
</div></section><section class="chapter"><h2 id="avoid-redundant-constructs" data-toc="avoid-redundant-constructs">Avoid redundant constructs</h2><p id="-9es39t_382">In general, if a certain syntactic construction in Kotlin is optional and highlighted by the IDE as redundant, you should omit it in your code. Do not leave unnecessary syntactic elements in code just &quot;for clarity&quot;.</p><section class="chapter"><h3 id="unit-return-type" data-toc="unit-return-type">Unit return type</h3><p id="-9es39t_386">If a function returns Unit, the return type should be omitted:</p><div class="code-block" data-lang="kotlin">
fun foo() { // &quot;: Unit&quot; is omitted here

}
</div></section><section class="chapter"><h3 id="semicolons" data-toc="semicolons">Semicolons</h3><p id="-9es39t_388">Omit semicolons whenever possible.</p></section><section class="chapter"><h3 id="string-templates" data-toc="string-templates">String templates</h3><p id="-9es39t_389">Don't use curly braces when inserting a simple variable into a string template. Use curly braces only for longer expressions:</p><div class="code-block" data-lang="kotlin">
println(&quot;$name has ${children.size} children&quot;)
</div><p id="-9es39t_391">Use <a href="strings.html#multi-dollar-string-interpolation" id="-9es39t_393">multi-dollar string interpolation</a> to treat the dollar sign chars <code class="code" id="-9es39t_394">$</code> as string literals:</p><div class="code-block" data-lang="kotlin">
val KClass&lt;*&gt;.jsonSchema : String
    get() = $$&quot;&quot;&quot;
        {
            &quot;$schema&quot;: &quot;https://json-schema.org/draft/2020-12/schema&quot;,
            &quot;$id&quot;: &quot;https://example.com/product.schema.json&quot;,
            &quot;$dynamicAnchor&quot;: &quot;meta&quot;,
            &quot;title&quot;: &quot;$${simpleName ?: qualifiedName ?: &quot;unknown&quot;}&quot;,
            &quot;type&quot;: &quot;object&quot;
        }
        &quot;&quot;&quot;
</div></section></section><section class="chapter"><h2 id="idiomatic-use-of-language-features" data-toc="idiomatic-use-of-language-features">Idiomatic use of language features</h2><section class="chapter"><h3 id="immutability" data-toc="immutability">Immutability</h3><p id="-9es39t_414">Prefer using immutable data to mutable. Always declare local variables and properties as <code class="code" id="-9es39t_417">val</code> rather than <code class="code" id="-9es39t_418">var</code> if they are not modified after initialization.</p><p id="-9es39t_415">Always use immutable collection interfaces (<code class="code" id="-9es39t_419">Collection</code>, <code class="code" id="-9es39t_420">List</code>, <code class="code" id="-9es39t_421">Set</code>, <code class="code" id="-9es39t_422">Map</code>) to declare collections which are not mutated. When using factory functions to create collection instances, always use functions that return immutable collection types when possible:</p><div class="code-block" data-lang="kotlin">
// Bad: use of a mutable collection type for value which will not be mutated
fun validateValue(actualValue: String, allowedValues: HashSet&lt;String&gt;) { ... }

// Good: immutable collection type used instead
fun validateValue(actualValue: String, allowedValues: Set&lt;String&gt;) { ... }

// Bad: arrayListOf() returns ArrayList&lt;T&gt;, which is a mutable collection type
val allowedValues = arrayListOf(&quot;a&quot;, &quot;b&quot;, &quot;c&quot;)

// Good: listOf() returns List&lt;T&gt;
val allowedValues = listOf(&quot;a&quot;, &quot;b&quot;, &quot;c&quot;)
</div></section><section class="chapter"><h3 id="default-parameter-values" data-toc="default-parameter-values">Default parameter values</h3><p id="-9es39t_423">Prefer declaring functions with default parameter values to declaring overloaded functions.</p><div class="code-block" data-lang="kotlin">
// Bad
fun foo() = foo(&quot;a&quot;)
fun foo(a: String) { /*...*/ }

// Good
fun foo(a: String = &quot;a&quot;) { /*...*/ }
</div></section><section class="chapter"><h3 id="type-aliases" data-toc="type-aliases">Type aliases</h3><p id="-9es39t_425">If you have a functional type or a type with type parameters which is used multiple times in a codebase, prefer defining a type alias for it:</p><div class="code-block" data-lang="kotlin">
typealias MouseClickHandler = (Any, MouseEvent) -&gt; Unit
typealias PersonIndex = Map&lt;String, Person&gt;
</div><p id="-9es39t_427">If you use a private or internal type alias for avoiding name collision, prefer the <code class="code" id="-9es39t_428">import ... as ...</code> mentioned in <a href="packages.html" id="-9es39t_429">Packages and Imports</a>.</p></section><section class="chapter"><h3 id="lambda-parameters" data-toc="lambda-parameters">Lambda parameters</h3><p id="-9es39t_430">In lambdas which are short and not nested, it's recommended to use the <code class="code" id="-9es39t_431">it</code> convention instead of declaring the parameter explicitly. In nested lambdas with parameters, always declare parameters explicitly.</p></section><section class="chapter"><h3 id="returns-in-a-lambda" data-toc="returns-in-a-lambda">Returns in a lambda</h3><p id="-9es39t_432">Avoid using multiple labeled returns in a lambda. Consider restructuring the lambda so that it will have a single exit point. If that's not possible or not clear enough, consider converting the lambda into an anonymous function.</p><p id="-9es39t_433">Do not use a labeled return for the last statement in a lambda.</p></section><section class="chapter"><h3 id="named-arguments" data-toc="named-arguments">Named arguments</h3><p id="-9es39t_434">Use the named argument syntax when a method takes multiple parameters of the same primitive type, or for parameters of <code class="code" id="-9es39t_436">Boolean</code> type, unless the meaning of all parameters is absolutely clear from context.</p><div class="code-block" data-lang="kotlin">
drawSquare(x = 10, y = 10, width = 100, height = 100, fill = true)
</div></section><section class="chapter"><h3 id="conditional-statements" data-toc="conditional-statements">Conditional statements</h3><p id="-9es39t_437">Prefer using the expression form of <code class="code" id="-9es39t_443">try</code>, <code class="code" id="-9es39t_444">if</code>, and <code class="code" id="-9es39t_445">when</code>.</p><div class="code-block" data-lang="kotlin">
return if (x) foo() else bar()
</div><div class="code-block" data-lang="kotlin">
return when(x) {
    0 -&gt; &quot;zero&quot;
    else -&gt; &quot;nonzero&quot;
}
</div><p id="-9es39t_440">The above is preferable to:</p><div class="code-block" data-lang="kotlin">
if (x)
    return foo()
else
    return bar()
</div><div class="code-block" data-lang="kotlin">
when(x) {
    0 -&gt; return &quot;zero&quot;
    else -&gt; return &quot;nonzero&quot;
}
</div></section><section class="chapter"><h3 id="if-versus-when" data-toc="if-versus-when">if versus when</h3><p id="-9es39t_446">Prefer using <code class="code" id="-9es39t_451">if</code> for binary conditions instead of <code class="code" id="-9es39t_452">when</code>. For example, use this syntax with <code class="code" id="-9es39t_453">if</code>:</p><div class="code-block" data-lang="kotlin">
if (x == null) ... else ...
</div><p id="-9es39t_448">Instead of this one with <code class="code" id="-9es39t_454">when</code>:</p><div class="code-block" data-lang="kotlin">
when (x) {
    null -&gt; // ...
    else -&gt; // ...
}
</div><p id="-9es39t_450">Prefer using <code class="code" id="-9es39t_455">when</code> if there are three or more options.</p></section><section class="chapter"><h3 id="guard-conditions-in-when-expression" data-toc="guard-conditions-in-when-expression">Guard conditions in when expression</h3><p id="-9es39t_456">Use parentheses when combining multiple boolean expressions in <code class="code" id="-9es39t_460">when</code> expressions or statements with <a href="control-flow.html#guard-conditions-in-when-expressions" id="-9es39t_461">guard conditions</a>:</p><div class="code-block" data-lang="kotlin">
when (status) {
    is Status.Ok if (status.info.isEmpty() || status.info.id == null) -&gt; &quot;no information&quot;
}
</div><p id="-9es39t_458">Instead of:</p><div class="code-block" data-lang="kotlin">
when (status) {
    is Status.Ok if status.info.isEmpty() || status.info.id == null -&gt; &quot;no information&quot;
}
</div></section><section class="chapter"><h3 id="nullable-boolean-values-in-conditions" data-toc="nullable-boolean-values-in-conditions">Nullable Boolean values in conditions</h3><p id="-9es39t_462">If you need to use a nullable <code class="code" id="-9es39t_463">Boolean</code> in a conditional statement, use <code class="code" id="-9es39t_464">if (value == true)</code> or <code class="code" id="-9es39t_465">if (value == false)</code> checks.</p></section><section class="chapter"><h3 id="loops" data-toc="loops">Loops</h3><p id="-9es39t_466">Prefer using higher-order functions (<code class="code" id="-9es39t_468">filter</code>, <code class="code" id="-9es39t_469">map</code> etc.) to loops. Exception: <code class="code" id="-9es39t_470">forEach</code> (prefer using a regular <code class="code" id="-9es39t_471">for</code> loop instead, unless the receiver of <code class="code" id="-9es39t_472">forEach</code> is nullable or <code class="code" id="-9es39t_473">forEach</code> is used as part of a longer call chain).</p><p id="-9es39t_467">When making a choice between a complex expression using multiple higher-order functions and a loop, understand the cost of the operations being performed in each case and keep performance considerations in mind.</p></section><section class="chapter"><h3 id="loops-on-ranges" data-toc="loops-on-ranges">Loops on ranges</h3><p id="-9es39t_474">Use the <code class="code" id="-9es39t_476">..&lt;</code> operator to loop over an open-ended range:</p><div class="code-block" data-lang="kotlin">
for (i in 0..n - 1) { /*...*/ }  // bad
for (i in 0..&lt;n) { /*...*/ }  // good
</div></section><section class="chapter"><h3 id="strings" data-toc="strings">Strings</h3><p id="-9es39t_477">Prefer string templates to string concatenation.</p><p id="-9es39t_478">Prefer multiline strings to embedding <code class="code" id="-9es39t_482">\n</code> escape sequences into regular string literals.</p><p id="-9es39t_479">To maintain indentation in multiline strings, use <code class="code" id="-9es39t_483">trimIndent</code> when the resulting string does not require any internal indentation, or <code class="code" id="-9es39t_484">trimMargin</code> when internal indentation is required:</p><div class="code-block" data-lang="kotlin" data-runnable="true">
fun main() {
//sampleStart
    println(&quot;&quot;&quot;
     Not
     trimmed
     text
     &quot;&quot;&quot;
    )

    println(&quot;&quot;&quot;
     Trimmed
     text
     &quot;&quot;&quot;.trimIndent()
    )

    println()

    val a = &quot;&quot;&quot;Trimmed to margin text:
            |if(a &gt; 1) {
            |    return a
            |}&quot;&quot;&quot;.trimMargin()

   println(a)
//sampleEnd
}
</div><p id="-9es39t_481">Learn the difference between <a href="java-to-kotlin-idioms-strings.html#use-multiline-strings" id="-9es39t_485">Java and Kotlin multiline strings</a>.</p></section><section class="chapter"><h3 id="functions-vs-properties" data-toc="functions-vs-properties">Functions vs properties</h3><p id="-9es39t_486">In some scenarios, functions with no arguments might be interchangeable with read-only properties. Although the semantics are similar, there are some stylistic conventions on when to prefer one to another.</p><p id="-9es39t_487">Prefer a property over a function when the underlying algorithm:</p><ul class="list _bullet" id="-9es39t_488"><li class="list__item" id="-9es39t_489"><p id="-9es39t_492">Does not throw.</p></li><li class="list__item" id="-9es39t_490"><p id="-9es39t_493">Is cheap to calculate (or cached on the first run).</p></li><li class="list__item" id="-9es39t_491"><p id="-9es39t_494">Returns the same result over invocations if the object state hasn't changed.</p></li></ul></section><section class="chapter"><h3 id="extension-functions" data-toc="extension-functions">Extension functions</h3><p id="-9es39t_495">Use extension functions liberally. Every time you have a function that works primarily on an object, consider making it an extension function accepting that object as a receiver. To minimize API pollution, restrict the visibility of extension functions as much as it makes sense. As necessary, use local extension functions, member extension functions, or top-level extension functions with private visibility.</p></section><section class="chapter"><h3 id="infix-functions" data-toc="infix-functions">Infix functions</h3><p id="-9es39t_496">Declare a function as <code class="code" id="-9es39t_498">infix</code> only when it works on two objects which play a similar role. Good examples: <code class="code" id="-9es39t_499">and</code>, <code class="code" id="-9es39t_500">to</code>, <code class="code" id="-9es39t_501">zip</code>. Bad example: <code class="code" id="-9es39t_502">add</code>.</p><p id="-9es39t_497">Do not declare a method as <code class="code" id="-9es39t_503">infix</code> if it mutates the receiver object.</p></section><section class="chapter"><h3 id="factory-functions" data-toc="factory-functions">Factory functions</h3><p id="-9es39t_504">If you declare a factory function for a class, avoid giving it the same name as the class itself. Prefer using a distinct name, making it clear why the behavior of the factory function is special. Only if there is really no special semantics, you can use the same name as the class.</p><div class="code-block" data-lang="kotlin">
class Point(val x: Double, val y: Double) {
    companion object {
        fun fromPolar(angle: Double, radius: Double) = Point(...)
    }
}
</div><p id="-9es39t_506">If you have an object with multiple overloaded constructors that don't call different superclass constructors and can't be reduced to a single constructor including parameters with default values, prefer to replace the overloaded constructors with factory functions.</p></section><section class="chapter"><h3 id="platform-types" data-toc="platform-types">Platform types</h3><p id="-9es39t_507">A public function/method returning an expression of a platform type must declare its Kotlin type explicitly:</p><div class="code-block" data-lang="kotlin">
fun apiCall(): String = MyJavaApi.getProperty(&quot;name&quot;)
</div><p id="-9es39t_509">Any property (package-level or class-level) initialized with an expression of a platform type must declare its Kotlin type explicitly:</p><div class="code-block" data-lang="kotlin">
class Person {
    val name: String = MyJavaApi.getProperty(&quot;name&quot;)
}
</div><p id="-9es39t_511">A local value initialized with an expression of a platform type may or may not have a type declaration:</p><div class="code-block" data-lang="kotlin">
fun main() {
    val name = MyJavaApi.getProperty(&quot;name&quot;)
    println(name)
}
</div></section><section class="chapter"><h3 id="scope-functions-apply-with-run-also-let" data-toc="scope-functions-apply-with-run-also-let">Scope functions apply/with/run/also/let</h3><p id="-9es39t_513">Kotlin provides a set of functions to execute a block of code in the context of a given object: <code class="code" id="-9es39t_514">let</code>, <code class="code" id="-9es39t_515">run</code>, <code class="code" id="-9es39t_516">with</code>, <code class="code" id="-9es39t_517">apply</code>, and <code class="code" id="-9es39t_518">also</code>. For the guidance on choosing the right scope function for your case, refer to <a href="scope-functions.html" id="-9es39t_519">Scope Functions</a>.</p></section></section><section class="chapter"><h2 id="coding-conventions-for-libraries" data-toc="coding-conventions-for-libraries">Coding conventions for libraries</h2><p id="-9es39t_520">When writing libraries, it's recommended to follow an additional set of rules to ensure API stability:</p><ul class="list _bullet" id="-9es39t_521"><li class="list__item" id="-9es39t_523"><p id="-9es39t_526">Always explicitly specify member visibility (to avoid accidentally exposing declarations as public API).</p></li><li class="list__item" id="-9es39t_524"><p id="-9es39t_527">Always explicitly specify function return types and property types (to avoid accidentally changing the return type when the implementation changes).</p></li><li class="list__item" id="-9es39t_525"><p id="-9es39t_528">Provide <a href="kotlin-doc.html" id="-9es39t_529">KDoc</a> comments for all public members, except for overrides that do not require any new documentation (to support generating documentation for the library).</p></li></ul><p id="-9es39t_522">Learn more about best practices and ideas to consider when writing an API for your library in the <a href="api-guidelines-introduction.html" id="-9es39t_530" data-tooltip="This guide contains a summary of best practices and ideas to consider when designing libraries.">Library authors' guidelines</a>.</p></section><div class="last-modified">12 August 2026</div><div data-feedback-placeholder="true"></div><div class="navigation-links _bottom"><a href="visibility-modifiers.html" class="navigation-links__prev">Visibility modifiers</a><a href="idioms.html" class="navigation-links__next">Idioms</a></div></article><div id="disqus_thread"></div></div></section></main></div><script src="custom-frontend-app/app.js?122"></script></body></html>
